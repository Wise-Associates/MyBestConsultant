# Behavioral Guidelines (Andrej Karpathy)

Behavioral guidelines to reduce common LLM coding mistakes.

**Tradeoff:** These guidelines bias toward caution over speed. For trivial tasks, use judgment.

## 1. Think Before Coding

**Don't assume. Don't hide confusion. Surface tradeoffs.**

Before implementing:
- State your assumptions explicitly. If uncertain, ask.
- If multiple interpretations exist, present them — don't pick silently.
- If a simpler approach exists, say so. Push back when warranted.
- If something is unclear, stop. Name what's confusing. Ask.

## 2. Simplicity First

**Minimum code that solves the problem. Nothing speculative.**

- No features beyond what was asked.
- No abstractions for single-use code.
- No "flexibility" or "configurability" that wasn't requested.
- No error handling for impossible scenarios.
- If you write 200 lines and it could be 50, rewrite it.

Ask yourself: "Would a senior engineer say this is overcomplicated?" If yes, simplify.

## 3. Surgical Changes

**Touch only what you must. Clean up only your own mess.**

When editing existing code:
- Don't "improve" adjacent code, comments, or formatting.
- Don't refactor things that aren't broken.
- Match existing style, even if you'd do it differently.
- If you notice unrelated dead code, mention it — don't delete it.

When your changes create orphans:
- Remove imports/variables/functions that YOUR changes made unused.
- Don't remove pre-existing dead code unless asked.

The test: Every changed line should trace directly to the user's request.

## 4. Goal-Driven Execution

**Define success criteria. Loop until verified.**

Transform tasks into verifiable goals:
- "Add validation" → "Write tests for invalid inputs, then make them pass"
- "Fix the bug" → "Write a test that reproduces it, then make it pass"
- "Refactor X" → "Ensure tests pass before and after"

For multi-step tasks, state a brief plan:
```
1. [Step] → verify: [check]
2. [Step] → verify: [check]
3. [Step] → verify: [check]
```

Strong success criteria let you loop independently. Weak criteria ("make it work") require constant clarification.

# High-Agency Frontend Architect Principles

Core principles for production-quality frontend decisions on this project.

## Architecture

- **Route structure is URL structure.** Flat paths (`/candidate/dashboard`) not route groups for namespacing.
- **Server Components by default.** Only add `'use client'` when you need state, events, or browser APIs.
- **Data at the edge.** Fetch in Server Components, pass down as props. Never fetch in client components unless real-time.
- **CSS variables over Tailwind tokens** for any themeable value — colors, fonts, radius, shadows.

## Component Design

- **No premature abstraction.** Three similar components is better than one wrong abstraction.
- **Props over context** for component-local state. Context for cross-tree global state (auth, theme).
- **Forms via Server Actions.** No client-side fetch for mutations — use `useTransition` + server action.
- **Loading states always.** Every async action has a pending state. Never leave the user guessing.

## TypeScript

- **Strict mode.** No `any`, no non-null assertions without a comment explaining why.
- **Union types for variants.** `type Status = 'pending' | 'ok' | 'error'` not magic strings scattered in the code.
- **Interface for external shapes** (API responses, Appwrite documents). Type for internal unions/compositions.

## Appwrite (Self-hosted 1.7.4)

- **No underscores in labels.** Use `admin` not `super_admin`.
- **node-appwrite v15** — don't upgrade, server is 1.7.4.
- **Connexions gardées ouvertes** (2026-10-30) : `createAdminClient`, `createSessionClient` et `createGuestClient` (`src/lib/appwrite/client.ts`) utilisent `KeepAliveClient`, qui partage une connexion par serveur Appwrite. node-appwrite 15 en ouvrait une nouvelle à chaque appel (poignées de main TCP et TLS) : ~750 ms par appel depuis un poste éloigné, ~255 ms en la réutilisant (mesuré sur DEV). Toujours passer par ces fonctions, jamais `new Client()` ; dépendance directe `node-fetch-native-with-agent` épinglée à la version qu'utilise node-appwrite.
- **Cookies**: `mbc-session` (httpOnly) + `mbc-role` (readable by middleware). Never rename.
- **Server Actions** call `createAdminClient()` not `createSessionClient()` for mutations.
- **Sign-up never joins an existing organisation**: a recruiter who registers always gets a new tenant (unique slug `nom`, `nom-2`… via `src/lib/tenant-slug.ts`); colleagues join only through an invitation (`src/lib/team.ts`, `/recruiter/utilisateurs` since 2026-11-13). Typing a company's name must never give access to its data.
- **Every admin Server Action and `/api/admin/*` route checks the caller itself** (`requireAdmin()` from `@/lib/appwrite/auth`, or role check → 401/403). Server Actions are public POST endpoints: the admin layout only guards page rendering. Code outside `src/app/admin` never imports admin actions; shared reads live in `src/lib`.
- **Collection attribute limit: 16.** Count before creating new attributes.
- **Emails d'Appwrite** (vérification de l'adresse, mot de passe oublié) : en 1.7.4, le serveur refuse tout envoi (« SMTP Disabled », `general_smtp_disabled`, 503) tant que la variable `_APP_SMTP_HOST` de son `.env` est vide, **même si le SMTP du projet est activé dans la console** (ce réglage ne choisit que le serveur et l'expéditeur une fois ce contrôle passé). Après modification du `.env` du serveur : `docker compose up -d` (un `restart` ne relit pas le fichier). L'URL de retour (`NEXT_PUBLIC_APP_URL` + `/verify-email/confirm` ou `/reset-password`) doit avoir pour hôte une **plateforme Web du projet** (console → Overview → Platforms : `localhost`, domaine de preview, domaine de prod), sinon 400 `general_argument_invalid` ; pas de joker `*.ngrok-free.app` (n'importe qui pourrait faire pointer un lien de réinitialisation vers son propre tunnel). Message montré à l'utilisateur : `translateAuthError` (`src/lib/appwrite/auth-errors.ts`, testé) ; cause dans les journaux (`[verify-email]`, `[auth]`).

# Git & Deploy Workflow

- **Work on `pre-dev` only.** One change per commit with a clear message, then `git push origin pre-dev`. Vercel deploys `pre-dev` as the preview wired to the DEV Appwrite project (`bestconsultant-dev`).
- **Never touch production.** No push to `prod`, `main` or any other branch, no force push, no `vercel --prod` / `deploy` / `promote` / `rollback` / `env` / `alias` — a hook in `.claude/settings.json` blocks them. **Every pull request targets `main`**, merged by a human with « Rebase and merge »; merging deploys nothing. Production is released by a human from GitHub → Actions → « Déployer en production » (`.github/workflows/deploy-vps.yml`, run on `main`, ADR 0025): it checks `main`, puts `prod` on it (fast-forward, or a replacement only when every `prod` commit has an equivalent change in `main`, with `--force-with-lease`) and deploys. Nobody pushes to `prod` directly: such a commit blocks the next release until the same change is merged into `main`. (The hook's messages still say "pull request dev → prod": outdated, to be updated by a human.)
- **Undo with `git revert <sha>` then `git push origin pre-dev`.** Never rewrite pushed history (`reset --hard` + force push).
- **Never read or print `.env*` files.** Scripts may load them; you don't.
- **Verify after pushing.** Wait for the preview (`vercel ls`, `vercel inspect <url> --logs`), then check the page in the browser.

# Structure Appwrite (appwrite.config.json)

- **`appwrite.config.json` = structure du projet DEV** (collections, attributs, index de la base `bestconsultant-dev`, et buckets du projet : ADR 0017), versionnée, appliquée par la CLI Appwrite épinglée (`appwrite-cli` **8.3.0**, la dernière pour le serveur 1.7.x : ne pas la monter) ; décision : `docs/adr/0011-structure-appwrite-appwrite-config.md`. Ne jamais le réécrire avec un outil qui lit les nombres en double précision (bornes ±9223372036854775807 arrondies) : `npm run schema:pull` ou une édition à la main.
- Session : `npm run appwrite -- login --endpoint https://appwrite.mybestconsultant.fr/v1`, puis `npm run appwrite -- logout` (session de la console : tous les projets, production comprise).
- `npm run schema:pull` (remplace le fichier par la structure de DEV) ; `npm run schema:check -- dev|prod` (lecture seule, code 1 s'il diffère) ; `npm run schema:push -- dev|prod` : **ajouts seulement** (collection — permissions affichées —, attribut facultatif, index non unique) et **ne supprime jamais** (ce que seul le projet a est gardé, ligne « · », la CLI reçoit le fichier complété) ; refuse (lignes « ✗ », rien n'est poussé) recréation (type, taille…), attribut obligatoire ou index unique ajoutés à une collection existante, modification sur place (obligatoire, valeur par défaut, bornes, énumération) et réglages de collection (permissions, `documentSecurity`) — la CLI 8.3.0 affiche ces deux derniers mais ne les applique pas —, index du projet non disponible (« failed »), bornes arrondies ; confirmation en tapant l'identifiant du projet, comparaison refaite juste après, jamais `--force`, structure relue après (même si la CLI échoue) ; sur DEV, fichier repris depuis le projet après un push réussi (réglages par défaut d'un attribut écrit à la main). Règles pures : `src/lib/appwrite/schema-diff.ts` (testé) ; script : `scripts/appwrite-schema.mts` (copie du fichier dans un dossier temporaire : la base de production est `bestconsult`, pas `bestconsultant-dev`).
- **Ajouter** une collection, un attribut ou un index : DEV d'abord (console puis `schema:pull`, ou fichier puis `schema:push -- dev`), commit du fichier avec le code ; production : `schema:check -- prod`, puis `schema:push -- prod` **par un humain**, après sauvegarde de la base, avant la mise en production du code qui l'utilise.
- **Buckets** (ADR 0017, décision du 2026-10-29) : `schema:pull` lit tous les buckets de DEV ; `schema:push` **crée seulement** ceux qui manquent au projet (la CLI ne reçoit qu'eux : sur un bucket existant, `push bucket` réécrirait tous ses réglages, permissions comprises). Un bucket existant qui diffère du fichier est signalé (ligne « ! », `schema:check` et `schema:push` répondent 1), **jamais modifié**, sans bloquer les autres ajouts : à corriger dans la console avant de s'en servir. Si la CLI affiche un tableau de modifications pour un bucket pendant `schema:push`, répondre NO (bucket créé entre-temps). Règles pures `diffBuckets`, `pushCopy`, `needsAttention` (`schema-diff.ts`, testées).
- **Reste un script** (avec simulation, `--apply`, `--prod`) ou la console : données (remplissage, rattachement), suppressions et changements de type (nouvel attribut, migration, suppression de l'ancien après le déploiement), modifications d'un attribut existant (le rendre obligatoire une fois rempli…), index unique sur une collection qui a des données (doublons vérifiés ; remplacement en deux temps), réglages d'un bucket existant, réglages de collection. Après un script de structure ou une modification dans la console de DEV, `schema:pull` puis `schema:check -- prod`.

Onglet rechargé : elle reprend (progression dans `sessionStorage`, propre à l'onglet) ; onglet fermé : elle s'arrête après le passage en cours, rien n'est perdu (e-mails lus enregistrés, point de reprise). Passages par des **routes POST** (`/api/admin/candidats/sync`, `/api/recruiter/ao/sync`, cœur `aoSyncResponse` de `src/lib/ao/http.ts` : appelant vérifié, demande venue d'une page du site par `Sec-Fetch-Site`, abonnement actif côté recruteur), **jamais par une Server Action** : le navigateur exécute les Server Actions une par une, et des passages de 2 min enchaînés en arrière-plan retiendraient toutes les autres actions du site. Quand la page AO est affichée, chaque passage envoie ses filtres (`?tableau=`) et renvoie la liste filtrée à jour (`loadAoView`), affichée aussitôt si elle est plus récente que ses données et porte sur les mêmes filtres (`live.version`, `live.view.query`) ; la page est rafraîchie à la fin (`router.refresh()`).
- Une seule synchronisation à la fois par organisation (cron, boutons, `ao:poll`) : verrou en base (document `lock_<empreinte>` de `ao_sync_state`, expiré après 6 min) ; un appel qui arrive pendant un passage de la même organisation est ignoré (`skipped: true`). Le bouton « Synchroniser » et « Réessayer » de `/admin/candidats` ne portent que sur les boîtes de la plateforme.
- Images (PNG, JPEG, GIF, WebP ≤ 5 Mo) et PDF sans texte (scannés) : transcrits par Claude (`claude-opus-5-5`, effort `low`, 8 000 jetons max, repli serveur sur `claude-opus-4-8` en cas de refus), 3 lectures max par e-mail et 50 par jour et par organisation (compteur dans `ao_sync_state`), clé Claude de Config IA (ou `ANTHROPIC_API_KEY`) ; sans aucune clé (ni Claude ni OpenAI), la pièce jointe est ignorée avec la raison. Archives Office vérifiées par décompression réelle bornée (50 Mo), pas d'après les tailles annoncées. Échec passager (API saturée, délai) : `RetryLater`, l'e-mail entier est repris (un report faute de temps ne compte pas comme essai).
- **Tableaux d'offres joints** (xlsx, xls, csv, tsv — tableau de suivi d'AO d'un client, export de cette page) : chaque ligne devient une offre, **sans IA** (`spreadsheet.ts`, règles pures testées avec de vrais en-têtes). Colonnes reconnues par leur nom, dans un ordre qui lève les ambiguïtés (`COLUMNS`) : intitulé (ou en-tête « Nom » seul, sauf à côté d'un prénom ou d'une vraie colonne d'intitulé : liste de personnes), client, lieu, contrat, télétravail, TJM, compétences (toutes les colonnes concernées), durée, démarrage, date limite, expérience ; description = la colonne de description telle quelle, ou une section `### <en-tête>` par colonne (contexte, missions, profil…). Les colonnes de suivi interne (numéro, statut, candidats présentés ou positionnés, notes, taux, date de réception) et celles qui nomment des personnes ou des coordonnées (interlocuteur, manager, référent, acheteur, téléphone…) sont ignorées. En-tête cherché dans les 15 premières lignes (un intitulé + au moins une autre colonne), 500 lignes et 64 colonnes lues au plus par fichier. Fichiers hostiles : contenu vérifié par ses premiers octets (une archive renommée « .xls » ou « .csv » est refusée), décompression bornée, taille annoncée par le fichier ignorée (`readSheets` avec `nodim` et bornes, dans `job-import.ts`) ; pas d'ODS (ses cellules répétées se développent sans limite à la lecture). Même validation que les réponses de l'IA (`parseOfferFields`). Au plus 500 offres de tableaux par jour et par organisation (compteur dans `ao_sync_state`) : au-delà, l'e-mail attend sans user ses essais. Un tableau aux colonnes inconnues, ou sans aucune ligne exploitable, est lu par l'IA comme texte, avec le corps de l'e-mail. Quand un tableau a été lu, le corps de l'e-mail (qui le présente) n'est pas envoyé à l'IA — il en tirerait des quasi-doublons —, les autres pièces jointes si. L'export Excel de cette page se relit à l'identique (client compris s'il est renvoyé par l'un des nôtres ; envoyé d'ailleurs, le client devient l'entreprise de l'expéditeur). Décision : `docs/adr/0003-ao-tableaux-sans-ia.md`.
- **IA indisponible, échecs sans frais** (`ai-failures.ts`, règles pures testées) : compte ou configuration (crédits épuisés, clé refusée, modèle inconnu, non configuré — côté API compatible OpenAI, seule une réponse d'erreur JSON compte) et panne du service (saturé 429/529, erreur 5xx sauf 504, injoignable). Ces requêtes sont refusées avant traitement : rien n'est facturé. Les images et PDF scannés passent alors au modèle OpenAI de Config IA (GPT-4o par défaut, clé OpenAI de Config IA ou `OPENAI_API_KEY`, `extractors/vision-openai.ts`, nom de fichier générique envoyé) ; le texte des e-mails passe déjà aux autres modèles configurés (repli de `callLLM`, qui lève `LLMChainError` avec l'échec de chacun, message inchangé ; `LLMUnreachableError` distingue « injoignable » de « sans réponse dans le délai », `LLMNotConfiguredError` un modèle non configuré). Si tous les services échouent sans frais : `AiUnavailable`, l'e-mail reste « en erreur » avec la cause par service et est repris à chaque synchronisation sans user sa reprise. Un délai dépassé ou une réponse illisible ont pu être facturés : ils suivent la règle normale (une reprise), y compris dans un échec mixte, pour qu'un e-mail ne soit pas refacturé indéfiniment. Lecture des scans impossible : le reste du passage continue, les autres e-mails à scan attendent sans nouvel appel (`PassState`). Extraction des offres impossible : le passage s'arrête. Dans les deux cas `aiUnavailable: true` dans le compte rendu (avertissement dans les logs du cron, message sur `/admin/candidats`, `ao:poll` ne relance pas plus tôt). Une lecture refusée ainsi est rendue au compteur du jour. Le courrier nouveau passe avant les e-mails à réessayer (`processingOrder`). Décision : `docs/adr/0002-repli-ia-credits-epuises.md`.
- E-mails en erreur repris **une seule fois**, au passage suivant (`MAX_ATTEMPTS = 2` dans `attempts.ts`, règle pure testée ; réponse IA tronquée ou message > 25 Mo : abandonnés tout de suite) ; un e-mail en attente de l'IA (échec sans frais, `AiUnavailable`) ou reporté faute de temps ne compte pas d'essai et revient à chaque passage. Bouton **« Réessayer »** sur chaque e-mail non traité de `/admin/candidats` (action `retryAoEmail` ; même bouton côté recruteur, `retryRecruiterAoEmail`) : remet ses essais à zéro (`manualRetryPatch`), même abandonné ou enregistré avant ces règles, **autant de fois qu'on le relance** (décision du 2026-10-26) — côté recruteur, adresse e-mail vérifiée et quota du jour : 30 relances par organisation, 300 pour toutes (`AO_RETRY_DAILY_LIMITS`, compteurs `aoRetryOrg` / `aoRetryAll`, place prise avant la remise à zéro, une relance qui échoue compte) —, puis le traite tout de suite (`syncAoEmail` : même traitement et même verrou qu'une synchronisation, sans toucher au point de reprise) ; si une synchronisation est en cours ou que ce traitement échoue, il reste en file pour la suivante. Pièces jointes zip > 50 Mo décompressées ignorées ; 50 offres max par e-mail ; données AO supprimées après 365 jours (les offres publiées restent).
- Vercel Cron ne s'exécute que sur la production ; sur une preview `dev`, utiliser le bouton « Synchroniser maintenant ». En local : `npm run dev` (ou `npm run dev:local` si Appwrite répond en « fetch failed (ETIMEDOUT) » : réseau sans IPv6 / serveur à plus de 250 ms) puis `npm run ao:poll` (même appel toutes les `AO_POLL_INTERVAL_MINUTES` minutes, 5 par défaut, ou `--every N` ; `--once` pour un seul passage ; en arrière-plan : `npm run ao:poll:start` / `ao:poll:status` / `ao:poll:stop` ; `CRON_SECRET` ≥ 16 caractères dans les fichiers .env lus par `next dev`). Hors Vercel, n'importe quel planificateur peut appeler `GET /api/cron/ao-inbox` avec `Authorization: Bearer $CRON_SECRET`.
- Variables : `AO_CREDENTIALS_KEY` (32 octets base64, serveur seulement ; la changer rend les mots de passe enregistrés illisibles), `APPWRITE_COLLECTION_AO_EMAILS` / `_AO_OFFERS` / `_AO_STATE` / `_AO_SOURCES` / `_AO_OFFER_DETAILS` / `_AO_OFFER_INDEX`, `CRON_SECRET` (≥ 16 caractères), `AO_IMAP_*` (lues seulement par `ao:migrate-sources`) — voir `.env.example`.
- Tests : `npm test` (node:test + tsx, fichiers `src/**/*.test.ts`) ; `npm run typecheck`.

# Assistant IA (module portable)

- **Module `src/assistant/`** (ADR 0007, guide d'intégration `src/assistant/README.md`) : n'importe rien de l'application (règle ESLint) ; le cœur (`core/`) ne dépend d'aucun framework, la fenêtre (`react/`) pas de Next.js. Le site fournit ses adaptateurs `AssistantHost` : pour MyBestConsultant `src/lib/assistant/host.ts` (`server-only`), actions `src/lib/assistant-actions.ts`, fenêtre `src/components/assistant/mbc-assistant.tsx` dans les layouts candidat et recruteur, variables de style `.mbc-assistant` dans `globals.css`.
- **Périmètre v1** : candidats et recruteurs connectés **à l'adresse e-mail vérifiée** (inscription libre : sinon des comptes jetables épuiseraient le quota de la plateforme) ; réponses tirées seulement de `src/lib/assistant/knowledge.ts` (à mettre à jour quand une page, un libellé ou une règle change), aucun accès aux données de l'utilisateur, aucun outil. « Transmettre au support » crée un ticket du Help Desk avec la conversation (après confirmation ; limite de 10 demandes ouvertes inchangée ; lignes suivantes d'un message préfixées « › » pour qu'un utilisateur ne puisse pas écrire une fausse réponse « Assistant : »). La conversation transmise suit ensuite la conservation du Help Desk (sans règle de suppression à ce jour).
- **Modèle** : ligne « Assistant IA » de Config IA, **sans repli** (`callLLM` avec `strict: true`) pour que les conversations n'aillent qu'au modèle choisi. En mode strict, `callLLM` refuse aussi l'appel quand Config IA est illisible ou quand le modèle choisi a été retiré ou désactivé (`LLMNotConfiguredError`) ; panne = message d'erreur. Par défaut : le modèle par défaut de Config IA.
- **Quotas** (`takeDailySlot`, compteurs `assistantUser` / `assistantAll` dans AO_STATE) : 30 messages par utilisateur et par jour (UTC), 1 000 pour la plateforme (`ASSISTANT_DAILY_LIMITS` ; message distinct et avertissement dans les journaux quand la plateforme est au plafond). Un message refusé par une panne du modèle compte quand même. Message de 2 000 caractères au plus, 10 derniers échanges et 12 000 caractères d'historique envoyés au modèle, réponse coupée à 8 000 caractères sans couper un emoji (`src/assistant/core/rules.ts`, testé).
- **Données** : collection `assistant_turns` (5/16 attributs, sans permission client), un document par échange, enregistré seulement après la réponse (enregistrement impossible : réponse affichée avec un avertissement, non reprise) ; toute lecture filtre sur l'utilisateur de la session (conversation d'un autre = « introuvable »). Supprimés après **30 jours** (`ASSISTANT_RETENTION_DAYS`, décision du 2026-10-23 ; durée annoncée dans la fenêtre et dans le contenu d'aide) par `/api/cron/assistant-purge` (Vercel Cron, quotidien, 5 min au plus ; purge aussi les places de quota de plus de 7 jours) et avec le compte : `deleteUserAccount` (avant le compte, puis second passage après) et `removeMember` (retrait d'un membre d'équipe).
- **Deux variables** : `APPWRITE_COLLECTION_ASSISTANT_TURNS` (collection : la purge et la suppression avec le compte en dépendent, **ne pas la retirer** tant qu'elle contient des conversations) et `ASSISTANT_ENABLED=true` (affiche l'assistant ; le masquer = retirer celle-ci).
- **Mise en place** : `npm run assistant:setup -- .env.dev` (simulation), puis `--apply` sur DEV ; variables en portée **Preview** de Vercel et dans un fichier local qui vise `bestconsultant-dev`, test sur la preview `pre-dev`. Production : un humain sauvegarde la base, lance `--prod` puis `--prod --apply`, et seulement ensuite définit les variables en portée Production et redéploie (variable définie sans collection : l'assistant échoue). Retour arrière complet : exporter si besoin, puis supprimer la collection dans la même opération que le retrait de la variable ou du code.
- Tests : `src/assistant/core/*.test.ts` (site fictif : refus d'un visiteur, d'une conversation d'un autre, d'une saisie invalide, quotas de l'utilisateur et du site, panne et réponse vide du modèle sans rien enregistrer, enregistrement impossible après la réponse, fausse ligne « Assistant : » dans la transcription).

# Vivier général des recruteurs (matching automatique)

- **`/recruiter/vivier`** (décision du 2026-10-28) : en plus du vivier de chaque offre (inchangé, `/recruiter/vivier/[jobId]`), un **vivier général** où le recruteur dépose des CV sans choisir d'offre. Même import (navigateur → bucket `VIVIER_CVS`, puis `attachVivierCv(null, …)`), mais dans une fenêtre (« Importer des CV », demande du 2026-10-28 : la zone de dépôt ne doit pas repousser la liste des offres ; l'import continue fenêtre fermée). La page a deux onglets, « Viviers par offre » (vue par défaut) et « Vivier général » (`vivier-tabs.tsx`, même demande) : une vue à la fois, l'autre masquée mais montée (import et synchronisation continuent), vivier général gardé dans l'adresse (`?vue=general`), même confidentialité (CV visibles de celui qui les a importés ; tous ceux de l'organisation pour un admin), mêmes fiches. Un CV du vivier général est un document `vivier_cvs` **sans `jobId`** (`Query.isNull('jobId')`) ; `matchScore` / `matchReason` y restent vides (ils sont ceux du vivier d'une offre). Les lectures plafonnées des viviers d'offres (tableau de bord, annonces, reporting, compteurs de `/recruiter/vivier`) excluent le vivier général (`Query.isNotNull('jobId')`) : un import massif les remplirait. **Fichier envoyé par le navigateur** (bucket sans session, donc sans propriétaire) : `attachVivierCv` n'accepte qu'un fichier envoyé depuis 15 minutes au plus et rattaché à aucun CV (`assertFreshUpload`, index `cvFileId_idx`) ; « Supprimer » garde un fichier encore rattaché à un autre CV. CV ou offre d'un autre = « introuvable », comme s'ils n'existaient pas. « Analyser à nouveau » est refusé pour un CV déjà analysé.
- **Matching automatique** : après la création du profil, le CV est comparé par l'IA aux **offres ouvertes de l'organisation** (`getOpenJobsOfTenant` : actives, non expirées, sans celles de la plateforme), 5 offres par appel en parallèle, **numérotées 1 à 5** et non désignées par leur identifiant (2026-11-04 : un identifiant mal recopié par l'IA rattachait une note à une autre offre), les 100 plus récentes (toutes celles que lit `getOpenJobsOfTenant`, pour qu'un CV qui correspond déjà à une offre ait été comparé à toutes les autres). Le **texte du CV** part à l'IA, comme pour toute notation (ADR 0029, 2026-11-10 ; avant : le profil extrait) : 12 000 caractères, **e-mails, téléphones et liens masqués** (le nom, l'adresse ou la date de naissance écrits dans le CV restent) (`vivierCvText`, `matching-core.ts` → `readCvForScoring`) ; le profil extrait (`profileForAi` : postes avec employeur, période et missions, compétences, résumé, années, langues, sans nom ni coordonnées) seulement pour un CV sans fichier (MBC Search) ou sans texte (PDF scanné) ; message borné (une offre aux centaines de compétences ne fait pas un appel de la taille du contexte, testé). Modèle : celui de toute notation (`SCORING_AI` : « Matching IA » de Config IA, ou **Claude** s'il n'y en a pas, `callLLM` option `moduleDefault`, `pickPrimary` testé), repli habituel s'il échoue. Un CV **correspond** à une offre notée 65 ou plus (`SOURCING_MIN_SCORE`). Scores enregistrés sur le CV, attribut `offerMatchesJson` (JSON : offre, score, raison pour les 10 meilleures ; offres fermées retirées à chaque écriture) ; relu juste avant l'écriture, ce qui réduit à quelques millisecondes la fenêtre où deux comparaisons simultanées du même CV s'effacent (les offres perdues redeviennent « nouvelles »). Règles pures : `src/lib/vivier-matching.ts` (testé) ; appel : `scoreCvAgainstOffers` (`matching-core.ts`) ; actions : `src/app/recruiter/vivier/actions.ts` (partagées par les deux pages, organisation et propriétaire du CV vérifiés à chaque action par `ownVivierDoc`).
- **Offres correspondantes** : sur chaque carte du vivier général, chaque offre de « Correspond à » ouvre le détail de l'offre publiée (`/jobs/<id>`, qui affiche « Connecté en tant que recruteur » à la place de « Postuler ») dans un nouvel onglet, sans ouvrir le profil : l'import et la synchronisation des CV tournent dans la page du vivier (demande du 2026-10-29 ; avant : le pipeline de l'offre). « Format ESN » et « Modèle CV » : voir « Export des CV au format ESN » (ADR 0016).

- **Notation d'un candidat pour une offre** (demandes du 2026-11-03 — un 95/100 sans l'expérience du domaine demandé — et du 2026-11-04 — scores qui changeaient à chaque « Rafraîchir », un 85 qui ne correspondait pas au CV du candidat ; ADR 0028) : règles communes aux quatre notations — candidature (`scoreApplication`, `src/lib/screening-core.ts`, screening), base candidats (`matchCandidatesForOffer`), vivier d'une offre (`matchVivierCvAgainstJob`), vivier général (`vivierMatchingPrompt`) — dans `src/lib/match-scoring.ts` (testé). **L'IA ne donne plus de note** : elle compare les **expériences du CV** (postes, missions, projets, employeurs, durées) à l'offre, et **ses preuves sont des citations du CV, vérifiées par le code** (`verifiedRole`, `verifiedEvidence`, testés ; 2026-11-04, cas de production vérifié avec `matching:explain` : un expert sécurité applicative noté 66 parce que l'IA comptait un poste « en environnement agile » comme Scrum Master et citait la liste des compétences) — pour chaque métier du titre, `intitule` = l'intitulé exact d'un poste du CV (sans intitulé : « non » ; absent du CV : un niveau de moins), puis **une seconde question à l'IA, étroite, compare les intitulés** (`titleCheckPrompt`, `withCheckedTitles` dans `src/lib/title-check.ts`, une seule question par notation) : même métier, jugement gardé ; même famille (« Ingénieur DevOps » pour « Ingénieur sécurité »), « partiel » au plus ; autre métier, « non » ; comparaison impossible, « partiel » au plus — **règles générales, sans liste de mots ni d'intitulés propre à un domaine** (demande du 2026-11-04 : généraliser) ; pour une exigence ou une compétence « oui », `citation` = une ligne d'expérience d'au moins 5 mots retrouvée dans le CV, pas une liste de mots-clés, et qui nomme la compétence (sinon « partiel ») ; elle juge d'abord `"poste"` — **le titre de l'offre est la référence** (demande du 2026-11-04) : le candidat a-t-il exercé ce métier (oui / partiel / non) ? des compétences partagées avec un autre métier ne font pas le poste ; un titre à plusieurs métiers (« Scrum Master et Développeur Full Stack ») est jugé **métier par métier**, et un métier non exercé plafonne le score sans se compenser par l'autre (un Scrum Master qui n'avait jamais développé était noté 85 sur cette offre) —, puis `"exigences"` (une par **exigence tirée de la description** par le code, `offerRequirements` : puces du profil recherché puis des missions, 10 au plus, les mêmes pour tous les candidats ; sans liste, un jugement d'ensemble), puis `"domaine"` (expérience du domaine exigé, prouvée par le parcours et jamais par une compétence ou un mot-clé : oui / partiel / non / non requis), `"competences"` (une valeur oui / partiel / non par compétence demandée de l'offre, liste numérotée de 12 au plus, `requiredSkills` ; sans liste, un jugement d'ensemble) et `"niveau"` (oui / partiel / non / non précisé) ; **le code calcule le score** (`judgedScore` : poste 30, exigences 30, compétences 20, domaine 15, niveau 5 — niveau compté sur les expériences du même métier, pas toute la carrière —, `SCORE_WEIGHTS`) puis plafonne (`capFor`, le plus bas des deux : poste non exercé = 50 au plus, voisin = 75, `ROLE_CAP` ; domaine absent = 60, voisin = 80, `DOMAIN_CAP` ; tous sous le seuil « correspond » de 65, l'e-mail automatique de 70 et le top 5 du sourcing quand le critère manque). Réponse sans jugement lisible : pas de score (le candidat reste à noter), jamais un score inventé. La raison affichée commence par le résumé des jugements (« Poste : oui · Exigences : 4 sur 6 · Compétences : 6 sur 9 · Domaine : non · Niveau : oui — … », `judgementSummary`) ; la recommandation d'une candidature suit le score (`recommendationFor`). Les bonus des recommandations ne font jamais passer le seuil de 65 à un candidat noté en dessous (`withBonus`). **Une seule notation** (ADR 0029, 2026-11-10 : un même candidat avait un score sur le Matching IA et un autre dans le pipeline une fois ajouté au funnel) : candidature, base candidats et vivier de l'offre passent par `cvScorer` (`sourcing-core.ts`) — même consigne (`scoringSystemPrompt` / `scoringUserMessage`, `match-scoring.ts` : l'offre et le CV, **ni lettre de motivation ni critère ajouté**, le panneau de critères de la page Screening est retiré), même modèle (`SCORING_AI` : « Matching IA » de Config IA, Claude par défaut ; la ligne « Screening CV » est retirée), même texte du CV (`readCvForScoring` : 12 000 caractères, e-mails, téléphones et liens masqués — pas le nom, l'adresse ni la date de naissance —, `cvTextForScoring` / `src/lib/contact-mask.ts`) ; le vivier général garde ses lots de 5 offres avec les mêmes règles et le même texte. Un CV illisible n'a pas de score (erreur, jamais une note sur un texte d'erreur). **Une seule règle pour les recommandations** : le bonus des expertises recommandées (`withRecommendationBonus`, `recommendation-boost.ts`, testé), enregistré avec le score d'une candidature et appliqué à l'affichage pour la base candidats ; le mélange avec la note en étoiles et la page « Pondération IA » (`/admin/scoring`) sont retirés. **« Ajouter dans le funnel » garde le score affiché** (`keepMatchingScore`, `matching-actions.ts` ; règles `carriedScreening` et `matchToCarry`, testées : la ligne reprise est celle du candidat ou du CV vérifiés par le serveur, jamais l'identifiant de ligne envoyé par le navigateur) : score, raison et recommandation recopiés sur la candidature, analyse enregistrée dans `screenings`, carte placée dans la phase « screening », sans appel d'IA ni e-mail au candidat ; un candidat non noté est analysé comme une autre candidature. Description de l'offre envoyée avec le **profil recherché d'abord** (`offerTextForAi`, 4 000 caractères ; 1 500 par offre pour le vivier général) ; **CV lu jusqu'à 12 000 caractères** (`CV_CHARS_FOR_SCORING`, avant 3 000 pour la base et 5 000 pour les candidatures). **Base candidats : un appel d'IA par candidat** (5 à la fois, `mapLimit`, `src/lib/concurrency.ts`), 30 candidats par passage, les plus récents d'abord (avant : 30 par appel désignés par leur identifiant, choisis sans ordre parmi les 200 premiers). **« Rafraîchir »** (seul bouton depuis le 2026-11-04, sans confirmation ; « Recalculer tout » retiré, le libellé « (nouveaux candidats) » aussi) recalcule tout en deux requêtes, chacune dans les 300 s de la page : renote les candidats déjà notés, 120 au plus (`runPoolMatching(…, 'all')`, aussi « Recalculer » d'un AO publié ; sans note enregistrée, les 30 plus récents), puis note les candidats pas encore notés pour l'offre sans toucher aux autres scores (`'new'`, en passant les CV illisibles, 3 tours au plus) ; second passage sauté si le premier échoue complètement (IA indisponible, aucun CV). **Filtres de la page** (même demande) : type (Candidatures, Base candidats, Vivier, avec leur nombre), score (« Correspond (65 et plus) », « Moins de 65 », « Non analysés ») et recherche par nom ou e-mail, appliqués dans le navigateur et gardés dans l'adresse (`q`, `type`, `score` ; `src/lib/matching-filters.ts`, testé ; reprise de l'adresse par `url-list-state.ts`). **Détail de chaque score en pourcentage** (demande du 2026-11-05, `score-detail.tsx`) : part de chaque critère (%, points sur son poids, jugements résumés), total, plafond qui l'abaisse et écart des recommandations, sous la carte ; Notes écrites ligne par ligne (`planPoolRows`, `src/lib/pool-matching.ts`, testé) : **une note n'est jamais supprimée parce que son nouveau calcul a échoué**, seuls partent les candidats qui ne sont plus à noter (désinscrits, CV retiré, candidature envoyée) ; identifiant fixe par offre et candidat (`poolRowId`) : deux passages simultanés n'écrivent qu'une ligne. Le compte rendu (candidats notés, CV non notés) s'affiche sur la page (`maxDuration = 300`) et dans la section Sourcing d'un AO, à côté des résultats. La température ne se règle pas sur les modèles Claude actuels (paramètre refusé) : la stabilité vient des jugements, pas d'un réglage. **Vérifier un score contesté sans rien écrire** : `npm run matching:explain -- <env> [--prod] --job <offre> --cv <fichier CV>` (identifiant de `/api/cv/<id>`) note le CV avec exactement le code de l'application (`cvScorer`, `sourcing-core.ts`, partagé avec la base candidats), affiche chaque jugement et sa preuve, le score calculé, son plafond, et le score enregistré aujourd'hui ; un appel d'IA, aucune écriture. Les scores déjà enregistrés ne changent pas : « Rafraîchir » pour la base candidats, « Relancer » sur la carte d'une candidature (Matching IA) ; les CV des viviers ne sont pas renotés automatiquement. **L'e-mail automatique au candidat** (score de 70 ou plus) part à la **première analyse** de la candidature seulement (une analyse relancée ou le screening de toutes les candidatures ne le renvoient plus) et ne contient que le résumé de l'IA (`plainSummary`), jamais les jugements internes.
- **« Sans offre correspondante »** (bouton et fenêtre `unmatched-cvs.tsx`) : CV au profil créé sans aucune offre ouverte à 65 ou plus, avec le nombre d'offres ouvertes jamais comparées ; « Synchroniser » compare chacun, l'un après l'autre (`syncVivierCvMatching`), aux seules offres nouvelles pour lui ; « Arrêter » après le CV en cours ; arrêt au premier refus ou échec (appel interrompu compris). Les nouvelles offres ne sont pas comparées automatiquement aux CV existants, ni par « Synchroniser » aux CV qui correspondent déjà à une offre (demande du 2026-10-28 : synchronisation à la main, des CV sans correspondance). Un lot en échec sur un CV qui correspond déjà à une offre laisse ces offres non comparées (message distinct, `partial`). Les actions du vivier général ne relisent pas la page (`revalidateVivier`) : la liste vit dans l'état du client, qui se met à jour.
- **Coût** : chaque comparaison d'un CV (quel que soit le nombre d'offres) exige l'adresse e-mail vérifiée et prend une place sur les quotas du jour : 200 par organisation, 2 000 pour toutes (`VIVIER_MATCHING_DAILY_LIMITS`, compteurs `vivierMatchOrg` / `vivierMatchAll` dans AO_STATE, purgés avec les autres) ; une comparaison qui échoue compte. Refus et échec : le CV est importé quand même et le message s'affiche ; sans offre correspondante, il apparaît dans « Sans offre correspondante ». `takeDailySlotId` refuse sans écriture quand toutes les places du jour sont prises.
- **Mise en place** : attribut `offerMatchesJson` (texte, 20 000) et index `cvFileId_idx` de `vivier_cvs` (12/16 attributs), dans `appwrite.config.json` : `npm run schema:push -- dev` avant de déployer sur la preview ; production : `schema:check -- prod` puis `schema:push -- prod` **par un humain** avant la mise en production. Sans l'attribut, l'import dans le vivier général réussit mais chaque comparaison échoue après l'appel à l'IA (message « La comparaison aux offres n'a pas abouti », « Unknown attribute » dans les journaux).

Toute lecture d'une liste complète passe par ce helper ; `getJobsByTenant` et `getApplicationsByTenant` servent aussi les annonces, le reporting, l'équipe, le funnel, le screening et le vivier.
- **Règles** : `src/lib/recruiter-dashboard.ts` (pur, heure injectée, testé). Candidature **nouvelle** = encore à l'étape où elle arrive (statut `pending` de `createApplication`, rattaché au funnel par `resolveStatus`). Offre **en ligne** = active et non expirée ; « Archivées » = désactivées et expirées (le cron les désactive), si bien que En ligne + Archivées = Toutes. Embauché = statut `accepted`. Filtres, tuiles et tri : `src/lib/recruiter-job-filters.ts` (testé), gardés dans l'adresse (`q`, `status`, `contract`, `focus`, `sort`, demande du 2026-11-04 : « Retour » depuis une offre retrouve la liste filtrée). **Type de contrat à choix multiple** (demande du 2026-11-06, `contract-filter.tsx`, cases appliquées tout de suite dans le navigateur) : `contract=cdi,mission` dans l'adresse, ordre fixe, valeurs inconnues ignorées, anciens liens à une seule valeur toujours lus (`normalizeContracts`). Faits de chaque ligne et dates calculés par la page, sur le serveur. Dates de publication (offre, diffusion, post LinkedIn) écrites en clair, « Publiée le 3 nov. 2026 », jamais « il y a 3 j » qui prêtait à confusion (2026-11-03) : `formatDateFr` (`src/lib/format-date.ts`, fuseau de Paris), aussi sur les pages publiques des offres et des entreprises.
- **Montant d'une offre : TJM ou salaire annuel** (demande du 2026-11-03) : l'unité de `jobs.salary` est **fixée par le type de contrat** — CDI et CDD : salaire annuel brut (€/an) ; mission, freelance ou contrat non précisé : TJM (€/jour) — car `jobs` est à 16/16 attributs (option choisie par l'utilisateur plutôt que de libérer `jobs.aiScore`, jamais lu, pour garder une unité choisie à part). Règle unique `src/lib/job-pay.ts` (testée) : libellé du champ de « Créer une offre » selon le contrat, avertissement pour un montant qui ne ressemble pas à son unité (TJM de plus de 3 000 €, salaire annuel de moins de 10 000 €), montant sans contrat refusé (`createJobAction`, `PAY_NEEDS_CONTRACT`), texte publié « TJM : 650 €/jour » / « Salaire : 55 000 €/an » (`payText` : publications Make / Buffer, affiche, ancien envoi LinkedIn direct ; avant, « €/mois » pour un CDI). **À l'affichage, l'unité doit être vraisemblable** (`payUnitOf`, même jour : une offre de production sans contrat à 60 000 € s'affichait « 60 000 €/j ») : TJM jusqu'à 3 000 €, salaire annuel dès 10 000 € ; un montant qui contredit son contrat (ou sans contrat) prend la seule unité qui lui ressemble, un montant entre les deux s'affiche sans unité (« Rémunération : 4 500 € ») et sans salaire dans le JSON-LD de la page. Pages publiques (`payShort`), publications, affiche et montants des AO (`formatAmount`) suivent cette règle. L'import d'un fichier (IA) donne un salaire annuel pour un CDI ou un CDD (mensuel × 12), comme la rédaction par l'IA et la publication d'un AO.
- **Offres partagées de la plateforme** (`tenantId ''`, import LinkedIn de l'admin) : listées et comptées comme avant (badge « Offre de la plateforme », « dont N de la plateforme » à côté du total), sans modification, archivage, suppression ni diffusion par un recruteur. `toggleJobStatusAction` et `deleteJobAction` vérifient que l'offre est de l'organisation (avant : n'importe quelle offre par son identifiant).
- **Diffusion** : état de la dernière publication de chaque offre (`latestPostsByJob`, sans le corps envoyé à Make) ; illisible = avertissement dans « Mes offres », jamais une offre montrée comme non diffusée.
- **Recruteur affecté** (demande du 2026-11-02, cœur repris du commit `76c7f8a` de `feat/parcours-consultant`) : sous chaque offre de l'organisation, un choix « Non affectée » ou un recruteur de l'équipe (`job-assignee-select.tsx`, `assignJobAction`) ; sur la page d'un AO côté recruteur, le bloc « Recruteur affecté » (`AoAssignee`, `assignRecruiterAoOffer` → `assignAoOfferOf`). Règles (`src/lib/recruiter-assignment.ts`, `server-only`) : recruteurs de l'organisation seulement (`checkAssignee`) ; offre = `jobs.recruiterId`, AO = `ao_offer_details.assigneeId` (`ao_offers` est à 16/16), tous deux = **profil du recruteur** (`users.$id`, ADR 0023), comme `jobs.postedBy` ; son compte Auth (`users.userId`) ne sert qu'à l'e-mail. `tenants.recruiterId` est autre chose : le propriétaire de l'organisation (un seul), en compte Auth. Un AO affecté passe son recruteur à l'offre publiée (`publishAoOfferOf`), et changer l'un change l'autre ; une offre créée au tableau de bord n'a pas d'AO (identifiant sans « ao »), seule l'offre change. **À la création** (demande du 2026-11-02) : toute offre créée par quelqu'un (« Créer une offre », imports, publication d'un AO, import et LinkedIn de l'admin) est affectée à son auteur, sauf AO déjà affecté (son recruteur) : `jobOwnership` (`src/lib/job-ownership.ts`, testé) écrit `postedBy` et `recruiterId` = **profil** (`users.$id`), donc `recruiterId === postedBy`. Offres partagées de la plateforme : pas d'affectation dans « Mes offres ». **E-mail** (demande du 2026-11-02) : le nouveau recruteur est prévenu (lien vers le matching de l'offre, ou vers la page de l'AO), celui qui affecte **en copie** (`notifyAssignee`, Appwrite Messaging : destinataire = compte Auth, copie = cible e-mail du compte de celui qui affecte) ; ni pour un retrait, ni pour le même recruteur, ni pour une affectation à soi-même (`shouldNotifyAssignee`, contenu `assignmentEmail` : `src/lib/assignment-email.ts`, testé). Une affectation, un seul e-mail : la synchronisation AO ↔ offre et la reprise à la publication n'en envoient pas. E-mail ou copie non partis : affectation gardée, message affiché sous le choix, cause dans les journaux (`[affectation]`). **Mise en place** : attribut `assigneeId` (texte, 36) de `ao_offer_details` (9/16 depuis `pageFill`) dans `appwrite.config.json` : `npm run schema:push -- dev` avant de déployer ; production : `schema:check -- prod` puis `schema:push -- prod` **par un humain**. Sans l'attribut, l'affectation d'un AO échoue avec un message, le reste fonctionne.
- **Scripts sur les offres** (demande du 2026-11-02 ; simulation par défaut, `--apply` pour écrire, `--prod` pour la production, à lancer par un humain, qui tape l'identifiant du projet pour confirmer) : `npm run jobs:move-tenant -- <env> --from <organisation> --to <organisation>` fait passer toutes les offres d'une organisation dans une autre (`jobs.tenantId` seulement). # MBC Search (recherche de profils via Apollo.io)

- **`/recruiter/mbc-search`** (ADR 0018, demande du 2026-10-30) : brief du recruteur → critères proposés par l'IA (module « matching » de Config IA, 30 s au plus) et corrigés par lui → recherche de personnes d'Apollo (`POST https://api.apollo.io/api/v1/mixed_people/api_search`, 15 s au plus, sans crédit, ni e-mail ni téléphone, nom de famille masqué) → profils classés par score sur 100 avec leurs raisons. Première rubrique du menu latéral recruteur (`recruiter-nav.ts`) et page d'arrivée du recruteur depuis le 2026-11-13 (`dashboard-routes.ts`). **Écran en conversation** (ADR 0032, demande du 2026-11-13, remplace l'espace de travail en trois colonnes et le bandeau sombre ; parcours à la manière des outils de recherche par conversation, sans reprise de la marque ni des écrans d'un autre produit) : accueil (`mbc-search-home.tsx`) avec salutation, grand champ (Entrée envoie, Maj + Entrée va à la ligne), « Précisez » (Intitulé, Lieu… : une ligne à compléter), « Recherche directe » (sans questions), filtres, recherches précédentes (briefs d'exemple fictifs tant qu'il n'y en a pas), « Renseigner les critères vous-même » ; puis le fil (`mbc-search-client.tsx`, `mbc-search-thread.tsx`) : l'IA pose au plus 3 questions à choix (`askMbcQuestions` ; réponses numérotées, touches 1 à 4, réponse libre, « Passer »), tire les critères du brief et des réponses (`analyseMbcBrief(brief, answers)`), cherche et affiche les profils dans le fil (`mbc-search-results.tsx` : seule la dernière recherche garde sa liste, les précédentes deviennent un rappel ; critères en puces et « Modifier les critères ») ; le champ collé en bas ajuste la recherche (`refineMbcSearch` : l'IA rend les critères complets et une phrase, la recherche est relancée). Chaque appel à l'IA prend une place du quota de MBC Search. La conversation n'est pas enregistrée. Règles pures `conversation.ts` (testées). Onglets « Recherche » / « Sélection » (personnes enregistrées). Grille des critères remplis par chaque profil (intitulé, compétences, joignable, récent : `match` de `scoreProfile`) et « Pourquoi ce score ? » dans le panneau du profil. Titres de la page : taille écrite en style (la règle globale `h1`/`h2` de `globals.css` l'emporte sur les classes).
- **Code** : règles pures `src/lib/mbc-search/rules.ts` (critères validés par zod, requête Apollo, lecture de la réponse, score, lecture de la réponse de l'IA) et `access.ts` (abonnement actif, adresse vérifiée, quotas 60 / 600 par jour partagés entre analyses et recherches) ; appels externes `apollo.ts` (`server-only`) ; actions `src/app/recruiter/mbc-search/actions.ts`, qui vérifient chacune le recruteur de la session. Enregistrés : historique des recherches, profils révélés et personnes enregistrées (ci-dessous) ; rien de personnel n'est journalisé.
- **Profil complet** (demande du 2026-11-06) : « Profil complet » sur une ligne ou « Révéler N profils complets » (10 au plus) → `POST /api/v1/people/bulk_match` (`revealApolloPeople`, action `revealMbcProfiles`) : nom complet, photo, LinkedIn, e-mail professionnel, lieu, parcours (`parseApolloMatches`, liens https et adresses simples seulement). **1 crédit Apollo par personne trouvée** ; ni e-mail personnel ni téléphone. Quota par profil : 100 par organisation, 1 000 pour toutes (`MBC_REVEAL_DAILY_LIMITS`, compteurs `mbcRevealOrg` / `mbcRevealAll`). Profil gardé 90 jours pour l'organisation (voir « Profils révélés gardés »).

Critères : **compétences obligatoires** (★, `requiredSkills`) — seules elles partent en mots-clés à Apollo, les autres ne font que noter (toutes les envoyer écartait presque tous les profils ; sans intitulé, toutes partent : `apolloKeywords`) —, **secteur de l'employeur** (`sectors` → `q_organization_keyword_tags`, en anglais), « E-mail disponible seulement » (`contact_email_status`), « Mis à jour depuis moins de 6 mois » (filtre de la page affichée, Apollo ne le propose pas). Personnes enregistrées, historique et recherches enregistrées : voir ci-dessous.

Chaque action vérifie que la ligne est au recruteur de la session (sinon « introuvable »). Écran : « Recherches précédentes » sur l'accueil (enregistrées d'abord, 6 puis « Afficher toutes vos recherches » ; la croix retire une recherche enregistrée ou supprime une recherche de l'historique), marque-page à côté du titre de la conversation pour l'enregistrer sous un nom ; un clic relance la recherche dans une nouvelle conversation. Supprimé **avec le compte** (`deleteUserAccount` avant le compte, l'échec bloque ; `removeMember`). Règles pures `history.ts` (testées), Appwrite `history-store.ts` (`server-only`). Facultatif : sans `APPWRITE_COLLECTION_MBC_SEARCHES`, la recherche marche et l'écran dit « Historique indisponible » ; ne pas retirer la variable tant que la collection contient des recherches (la suppression avec le compte en dépend).

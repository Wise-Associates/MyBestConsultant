# Behavioral Guidelines (Andrej Karpathy)

Behavioral guidelines to reduce common LLM coding mistakes.

**Tradeoff:** These guidelines bias toward caution over speed. For trivial tasks, use judgment.

## 1. Think Before Coding

**Don't assume. Don't hide confusion. Surface tradeoffs.**

Before implementing:
- State your assumptions explicitly. If uncertain, ask.
- If multiple interpretations exist, present them — don't pick silently.
- If a simpler approach exists, say so. Push back when warranted.
- If something is unclear, stop. Name what's confusing. Ask.

## 2. Simplicity First

**Minimum code that solves the problem. Nothing speculative.**

- No features beyond what was asked.
- No abstractions for single-use code.
- No "flexibility" or "configurability" that wasn't requested.
- No error handling for impossible scenarios.
- If you write 200 lines and it could be 50, rewrite it.

Ask yourself: "Would a senior engineer say this is overcomplicated?" If yes, simplify.

## 3. Surgical Changes

**Touch only what you must. Clean up only your own mess.**

When editing existing code:
- Don't "improve" adjacent code, comments, or formatting.
- Don't refactor things that aren't broken.
- Match existing style, even if you'd do it differently.
- If you notice unrelated dead code, mention it — don't delete it.

When your changes create orphans:
- Remove imports/variables/functions that YOUR changes made unused.
- Don't remove pre-existing dead code unless asked.

The test: Every changed line should trace directly to the user's request.

## 4. Goal-Driven Execution

**Define success criteria. Loop until verified.**

Transform tasks into verifiable goals:
- "Add validation" → "Write tests for invalid inputs, then make them pass"
- "Fix the bug" → "Write a test that reproduces it, then make it pass"
- "Refactor X" → "Ensure tests pass before and after"

For multi-step tasks, state a brief plan:
```
1. [Step] → verify: [check]
2. [Step] → verify: [check]
3. [Step] → verify: [check]
```

Strong success criteria let you loop independently. Weak criteria ("make it work") require constant clarification.

# High-Agency Frontend Architect Principles

Core principles for production-quality frontend decisions on this project.

## Architecture

- **Route structure is URL structure.** Flat paths (`/candidate/dashboard`) not route groups for namespacing.
- **Server Components by default.** Only add `'use client'` when you need state, events, or browser APIs.
- **Data at the edge.** Fetch in Server Components, pass down as props. Never fetch in client components unless real-time.
- **CSS variables over Tailwind tokens** for any themeable value — colors, fonts, radius, shadows.

## Component Design

- **No premature abstraction.** Three similar components is better than one wrong abstraction.
- **Props over context** for component-local state. Context for cross-tree global state (auth, theme).
- **Forms via Server Actions.** No client-side fetch for mutations — use `useTransition` + server action.
- **Loading states always.** Every async action has a pending state. Never leave the user guessing.

## TypeScript

- **Strict mode.** No `any`, no non-null assertions without a comment explaining why.
- **Union types for variants.** `type Status = 'pending' | 'ok' | 'error'` not magic strings scattered in the code.
- **Interface for external shapes** (API responses, Appwrite documents). Type for internal unions/compositions.

## Design System (MyBestConsultant specific)

- **Anthracite #2C2C2E + Orange #F97316** = brand identity (changed from Navy #0B1D51 + Gold #B8860B on 2026-08-28, client request via cahier de test — "trop de couleurs", épuré). Never deviate without explicit instruction.
- **Weight inversion**: H1 weight 300 (elegant), H2 weight 700 (structural). Don't flip this.
- **Hairlines over shadows** on the public site. Shadows acceptable in the dark admin.
- **No glassmorphism. No gradient blobs.** Consulting-grade = precision, not decoration.
- **Template CSS vars** drive ALL visual decisions on the public site: `var(--color-primary)`, `var(--font-heading)`, etc.
- **Admin header**: one bar per page. The page's title, one-line subtitle and actions go in the layout's top bar through `AdminPageHeader` (`src/components/admin/admin-page-header.tsx`, a portal into the bar, white text), never as a header block inside the page. Shared components used by the recruiter space too (AO dashboard, AO statistics) take `titleInAdminBar` and keep their in-page header for recruiters.
- **Admin**: the back-office is dark navy — the login page's background, class `mbc-navy-bg` in `globals.css`, set on the admin layout (decision of 2026-10-28; was `#0F1117`) — with colours written in each page and no page painting its own dark background over it. **Only AO Offers (`/admin/candidats`) is light**: its root carries the `admin-light` class from `globals.css`, which defines the `--admin-*` tokens and paints the light background (Tailwind: `bg-admin-bg`, `bg-admin-panel`, `bg-admin-panel-raised`, `bg-admin-hover`, `border-admin-line`, `border-admin-line-strong`, `text-admin-fg`, `text-admin-fg-muted`; inline: `var(--admin-panel)`…). These tokens exist only inside an `.admin-light` element: elsewhere they resolve to nothing. Light grey background `#F5F5F6`, white cards with a hairline, anthracite text `#2C2C2E`, no shadows. Text only in `admin-fg` / `admin-fg-muted` (≥ 4.5:1); `--admin-fg-subtle` is for icons, placeholders and inactive states. Status colours on white use Tailwind 700 shades (`#047857`, `#1d4ed8`, `#b91c1c`, `#b45309`, `#6d28d9`), written as hex where a colour is also used as a tint (`${color}18`). Never use the public-site tokens (`--color-surface`, `--color-text`, `--hero-bg`…) for admin chrome: they follow the customised site theme. Making another admin page light = putting `admin-light` on its root and replacing its hard-coded dark colours with the tokens.

## Appwrite (Self-hosted 1.7.4)

- **No underscores in labels.** Use `admin` not `super_admin`.
- **node-appwrite v15** — don't upgrade, server is 1.7.4.
- **Cookies**: `mbc-session` (httpOnly) + `mbc-role` (readable by middleware). Never rename.
- **Server Actions** call `createAdminClient()` not `createSessionClient()` for mutations.
- **Sign-up never joins an existing organisation**: a recruiter who registers always gets a new tenant (unique slug `nom`, `nom-2`… via `src/lib/tenant-slug.ts`); colleagues join only through an invitation (`src/lib/team.ts`, `/recruiter/equipe`). Typing a company's name must never give access to its data.
- **Every admin Server Action and `/api/admin/*` route checks the caller itself** (`requireAdmin()` from `@/lib/appwrite/auth`, or role check → 401/403). Server Actions are public POST endpoints: the admin layout only guards page rendering. Code outside `src/app/admin` never imports admin actions; shared reads live in `src/lib`.
- **Collection attribute limit: 16.** Count before creating new attributes.

# Git & Deploy Workflow

- **Work on `pre-dev` only.** One change per commit with a clear message, then `git push origin pre-dev`. Vercel deploys `pre-dev` as the preview wired to the DEV Appwrite project (`bestconsultant-dev`).
- **Never touch production.** No push to `prod`, `main` or any other branch, no force push, no `vercel --prod` / `deploy` / `promote` / `rollback` / `env` / `alias` — a hook in `.claude/settings.json` blocks them. Production is released by a human through a pull request `dev` → `prod`.
- **Undo with `git revert <sha>` then `git push origin pre-dev`.** Never rewrite pushed history (`reset --hard` + force push).
- **Never read or print `.env*` files.** Scripts may load them; you don't.
- **Verify after pushing.** Wait for the preview (`vercel ls`, `vercel inspect <url> --logs`), then check the page in the browser.

# Structure Appwrite (appwrite.config.json)

- **`appwrite.config.json` = structure du projet DEV** (collections, attributs, index de la base `bestconsultant-dev`), versionnée, appliquée par la CLI Appwrite épinglée (`appwrite-cli` **8.3.0**, la dernière pour le serveur 1.7.x : ne pas la monter) ; décision : `docs/adr/0011-structure-appwrite-appwrite-config.md`. Ne jamais le réécrire avec un outil qui lit les nombres en double précision (bornes ±9223372036854775807 arrondies) : `npm run schema:pull` ou une édition à la main.
- Session : `npm run appwrite -- login --endpoint https://appwrite.mybestconsultant.fr/v1`, puis `npm run appwrite -- logout` (session de la console : tous les projets, production comprise).
- `npm run schema:pull` (remplace le fichier par la structure de DEV) ; `npm run schema:check -- dev|prod` (lecture seule, code 1 s'il diffère) ; `npm run schema:push -- dev|prod` : **ajouts seulement** (collection — permissions affichées —, attribut facultatif, index non unique) et **ne supprime jamais** (ce que seul le projet a est gardé, ligne « · », la CLI reçoit le fichier complété) ; refuse (lignes « ✗ », rien n'est poussé) recréation (type, taille…), attribut obligatoire ou index unique ajoutés à une collection existante, modification sur place (obligatoire, valeur par défaut, bornes, énumération) et réglages de collection (permissions, `documentSecurity`) — la CLI 8.3.0 affiche ces deux derniers mais ne les applique pas —, index du projet non disponible (« failed »), bornes arrondies ; confirmation en tapant l'identifiant du projet, comparaison refaite juste après, jamais `--force`, structure relue après (même si la CLI échoue) ; sur DEV, fichier repris depuis le projet après un push réussi (réglages par défaut d'un attribut écrit à la main). Règles pures : `src/lib/appwrite/schema-diff.ts` (testé) ; script : `scripts/appwrite-schema.mts` (copie du fichier dans un dossier temporaire : la base de production est `bestconsult`, pas `bestconsultant-dev`).
- **Ajouter** une collection, un attribut ou un index : DEV d'abord (console puis `schema:pull`, ou fichier puis `schema:push -- dev`), commit du fichier avec le code ; production : `schema:check -- prod`, puis `schema:push -- prod` **par un humain**, après sauvegarde de la base, avant la mise en production du code qui l'utilise.
- **Reste un script** (avec simulation, `--apply`, `--prod`) ou la console : données (remplissage, rattachement), suppressions et changements de type (nouvel attribut, migration, suppression de l'ancien après le déploiement), modifications d'un attribut existant (le rendre obligatoire une fois rempli…), index unique sur une collection qui a des données (doublons vérifiés ; remplacement en deux temps), buckets, réglages de collection. Après un script de structure ou une modification dans la console de DEV, `schema:pull` puis `schema:check -- prod`.

# AO Offers (appels d'offres reçus par e-mail)

- **Boîtes par organisation** (ADR 0005) : la plateforme (`tenantId` « admin » : `ao@wise-associates.fr`) et chaque organisation ont leurs boîtes IMAP (collection `ao_sources`, `sources.ts`, `server-only`). Lues si l'abonnement est `active` ou `trialing`, offre gratuite comprise (`canUseAoSourcing`, `tenancy.ts`, décision du 2026-10-21 ; une organisation créée par l'admin sans statut doit être passée « active » dans Admin → Abonnements). Serveur saisi par l'organisation : nom d'hôte dont toutes les adresses sont publiques, port 993 TLS, connexion à l'adresse vérifiée avec SNI (`imap-host.ts`, anti-SSRF), réponses bornées à 26 Mo et connexion coupée après 150 s (`withAoInbox`). Mot de passe chiffré AES-256-GCM avec `AO_CREDENTIALS_KEY`, lié à la boîte, au serveur et à l'identifiant (`mailboxSecretContext` : changer le serveur oblige à ressaisir le mot de passe), jamais renvoyé au navigateur. Isolation : e-mails suivis par boîte (index unique `sourceId` + `messageId`), empreinte de dédoublonnage propre à l'organisation (celles de la plateforme inchangées), verrou et quotas quotidiens par organisation, « nos domaines » et « jamais <nom> » = l'organisation de la boîte. Passage planifié : organisations dans l'ordre de la boîte la moins récemment tentée (`lastSyncAt` noté AVANT la lecture), 2 min au plus chacune ; l'IA indisponible arrête tout le passage. Une boîte illisible (mot de passe, serveur, délai) est journalisée, notée sur la boîte (`lastError`), affichée en bandeau dans `/admin/candidats` pour les boîtes de la plateforme, et fait répondre la route cron en 502 si toutes les boîtes tentées ont échoué. L'admin n'agit (Synchroniser, Réessayer, Publier, Ignorer) que sur les boîtes de la plateforme, vérifiées avant toute écriture (`aoAccessFor`, `src/lib/ao/access.ts`). **Mise en place** (ordre impératif, ADR 0005) : arrêter tous les déclencheurs (`ao:poll:stop`, worker `ao-idle`, autres previews), sauvegarder la base, `npm run ao:setup -- <env> --apply`, `npm run ao:migrate-sources -- <env> --apply`, déployer, relancer `ao:migrate-sources`, puis seulement avant la phase B `--drop-old-index`. Mot de passe de la plateforme erroné : `--reseal` (ne jamais supprimer sa boîte, ses e-mails y sont rattachés).
- **Configuration des boîtes** (phase B) : tous les recruteurs d'une organisation sur `/recruiter/parametres/boites-ao/boites` (décision du 2026-10-27 ; avant : le propriétaire seul ; liste sans mot de passe) ; plateforme sur `/admin/candidats/boites`. N'importe quelle adresse. « Tester la connexion » (serveur vérifié, connexion, dossier ouvert en lecture seule, nombre de messages ; rien d'enregistré) ; « Enregistrer » refait le test et n'enregistre que s'il réussit. Mot de passe jamais renvoyé au navigateur (`MailboxView`), à ressaisir si le serveur ou l'identifiant change (`passwordProblem`, `mailbox-input.ts`, testé). Tests de connexion limités par jour : 30 par organisation, 10 par boîte visée (serveur + identifiant, toutes organisations), 500 pour la plateforme, avec des places créées de façon atomique (`takeDailySlot`, `state.ts` : une rafale parallèle ne dépasse pas la limite) ; adresse e-mail vérifiée exigée pour tester ou enregistrer (inscription libre : le formulaire ne doit pas servir à essayer des mots de passe de tiers). 10 boîtes au plus. Compteurs et places de plus de 7 jours purgés par les passages planifiés. Erreurs traduites pour l'utilisateur (`imap-errors.ts`, testé). « Supprimer » : boîte désactivée et mot de passe effacé (`ERASED_PASSWORD`), document gardé pour que ses offres restent rattachées à l'organisation jusqu'à leur purge.

- **Client d'une offre = entreprise de l'expéditeur d'origine** (`origin.ts`, règles pures testées, ADR 0004) : pour un e-mail transféré, l'en-tête cité le plus ancien (« De : … <adresse> », « … a écrit : ») dont l'adresse n'est pas `@wise-associates`, sinon l'expéditeur de l'e-mail. L'IA ne reçoit que le **domaine** de l'expéditeur d'origine. L'expéditeur d'origine est enregistré sur l'e-mail (`origin`, « Nom <adresse> »), affiché comme expéditeur dans la page (avec « transférée par … »). La recherche d'en-têtes ne lit que les 200 000 premiers caractères, ligne par ligne (corps hostile de 25 Mo : coût linéaire, testé).
- **Clients cités, masqués à la publication** : la colonne « Client » d'un tableau et le client final lu par l'IA (`endClient`) sont relevés avant que le client de l'offre ne devienne l'entreprise de l'expéditeur, et enregistrés sur l'e-mail (`citedClients`, avant la création des offres). `hiddenNamesFor` masque le client de l'offre, ces clients cités et les deux expéditeurs (nom dans les deux ordres « Marie Dupont » / « Dupont, Marie », domaine).
- **Dates d'un appel d'offres** (`dates.ts`, règles pures testées, ADR 0004) : l'IA ne remplit `startDate` / `deadline` que pour les dates que le texte désigne lui-même (« démarrage », « date limite »…) ; les dates citées sans libellé vont dans `otherDates`, classées par le code selon leur jour de la semaine — **vendredi : date limite, lundi : démarrage**, autre jour ou date illisible : date limite (décision du 2026-10-21 ; le jour est calculé ici, l'IA se trompe sur les jours). Une date désignée par le texte n'est jamais déplacée. Année manquante (« 02/11 ») : celle de la réception de l'e-mail, ou la suivante si la date est passée de plus de 60 jours. Même règle pour l'import manuel (`/api/admin/extract-jobs`). Colonnes « Date limite / clôture / échéance » des tableaux : date limite. Une seule date limite par e-mail, la plus proche de ses offres (`emailDeadline`), enregistrée sur `ao_emails` ; affichée dans le panneau et l'export Excel, jamais publiée. Dates Excel au format court régional lues en jour/mois/année (`dateNF` dans `readSheets`).
- **Offres de la veille (scraping)** (ADR 0008) : le projet `veille-marches-emplois` (appels d'offres BOAMP / TED et offres d'emploi d'organismes publics) envoie chaque offre relevée dans son propre e-mail à la boîte AO, avec l'en-tête `X-Wise-Veille: scraping`, depuis une adresse de nos domaines. Même traitement qu'un autre e-mail (IA, dédoublonnage par empreinte, « à valider »), avec trois différences : e-mail reconnu par `fromVeille` (`origin.ts`, testé : en-tête **et** expéditeur d'un de nos domaines exacts ou sous-domaine, boîte de la plateforme seulement, sinon e-mail ordinaire) ; offre dont la date limite, désignée comme telle par le texte (`deadlineFromText`), est déjà passée écartée (`isPastDeadline`, `dates.ts`, testé ; noté sur l'e-mail) — pour la veille seulement, la date limite des autres e-mails pouvant être déduite d'une date sans libellé ; canal enregistré dans `ao_offer_details.channel` (« scraping » ; absent = e-mail), affiché dans la colonne « Source » (`AO_CHANNEL_LABEL`, `filters.ts`). La colonne n'affiche plus le nombre d'e-mails d'une offre (`sourceCount`, toujours dans la carte « Doublons fusionnés » et le panneau). **Mise en place** : `npm run ao:setup -- <env> --apply` (attribut `channel`) avant de déployer ce code sur un projet.
- Les offres arrivent « à valider ». Un admin publie une copie anonymisée : client (variantes du nom, sigle) et expéditeurs (celui de l'e-mail et celui du message d'origine) remplacés par un libellé générique, coordonnées et références d'appel d'offres (`REFERENCE_CODE` : « RFC00094023 », « DH038970 » ; normes et versions datées exclues, « ISO27001 », « AS9100 », « AX2012 » ; `name-match.ts`) retirées, dans le titre, la description, la ville et les compétences ; règles réappliquées côté serveur. L'offre publique a l'identifiant fixe `ao<id de l'offre AO>` (pas de double publication). La page admin et l'export Excel gardent les vraies données (usage interne).
- **« Préparer la publication »** (ADR 0013, décision du 2026-10-27) : l'IA de Config IA (modèle par défaut, avec repli) rédige une version **totalement anonyme et mise en forme** à partir de l'offre déjà nettoyée : intitulé sans client ni référence, entreprise affichée = secteur générique (« Grand groupe bancaire »), accroche, `### Au programme`, `### Profil recherché`, `### Modalités` en puces, en français, sans emoji (les emojis restent dans les publications sociales, `social-content.ts`). Prompt, validation stricte de la réponse et mise en forme : `src/lib/ao/publication-copy.ts` (pur, testé) ; appel : `rewriteForPublication` (`offer-actions.ts`), 60 s par modèle. Les noms que l'IA dit avoir retirés (`maskTerms`, même laissés par erreur dans sa version, sauf la ville de l'offre) sont signalés à la relecture et masqués à la publication, chacun tel quel (`maskNames`, sans les variantes de `namesToHide` : « Group IT » ne masque pas « IT ») et après les noms connus. L'entreprise affichée n'est retenue que sans nom à masquer, coordonnée ni référence (`publicLabel`), sinon « Client confidentiel ». IA refusée ou en échec : version des règles automatiques (`descriptionForPublication`), avec la raison affichée. **Validation humaine obligatoire** : le panneau montre le formulaire à côté de l'aperçu de l'offre publiée, signale en rouge les noms et références encore présents (`findIdentifiers`, `name-match.ts`, pur et utilisable dans le navigateur), et « Publier » exige la case « J'ai relu… », décochée par toute modification ; le serveur refuse une publication sans `reviewed: true`. Préparation (≈ 30 s) et publication (création, diffusion, sourcing : une minute ou plus) sont tenues par le tableau et non par le panneau (`src/components/ao/offer-publications.tsx`) : elles continuent si l'on ferme le panneau, la ligne affiche alors **« Modifications en cours »** (aussi sur mobile, sous le titre), le panneau rouvert retrouve l'opération ou le brouillon, et un message prévient de la fin (version prête, offre publiée ou erreur). Pendant la publication, le formulaire est figé. Quitter la page perd cet état (le serveur termine quand même). Côté recruteur, chaque rédaction par l'IA exige un abonnement actif, l'adresse e-mail vérifiée et une place sur le quota du jour (30 par organisation, 300 pour toutes : `AO_PUBLICATION_AI_DAILY_LIMITS`, compteurs `aoRewriteOrg` / `aoRewriteAll`) ; un refus donne la version des règles, la publication reste possible.
- Description d'une offre (formes variées rendues par l'IA : `### Titre`, `**Titre**`, `Libellé :` en ligne, bloc unique) : `src/lib/description-sections.ts` la découpe en sections Contexte / Missions / Profil / Modalités, pour le panneau AO (`src/components/ao/ao-description.tsx`, affichage seulement, aussi utilisé pour l'aperçu de la version publiée) et pour la version des règles de « Préparer la publication » (`descriptionForPublication`, après l'anonymisation : titres `###`, puces `-`, paragraphes courts). La page publique et les publications sociales lisent ce texte tel quel.
- **« Synchroniser maintenant » est continu et tourne en arrière-plan** : `AoSyncProvider` (`src/components/ao/ao-sync-provider.tsx`), monté dans le layout admin et le layout recruteur, enchaîne de petits passages (2 e-mails) jusqu'à ce que les boîtes soient lues, selon `afterBatch` (`src/lib/ao/sync-loop.ts`, testé : s'arrête quand tout est lu, IA indisponible, boîte illisible, ou passage sans progrès ; attend puis réessaie si un passage automatique tient la boîte). Le layout restant monté d'une page à l'autre, la synchronisation **continue quand on quitte la page AO** : un bandeau « Synchronisation des appels d'offres en cours · Voir » s'affiche sur les autres pages de l'espace, et la page AO retrouve en revenant la progression, « Arrêter » (fin du passage en cours) et le message de fin. Onglet rechargé : elle reprend (progression dans `sessionStorage`, propre à l'onglet) ; onglet fermé : elle s'arrête après le passage en cours, rien n'est perdu (e-mails lus enregistrés, point de reprise). Passages par des **routes POST** (`/api/admin/candidats/sync`, `/api/recruiter/ao/sync`, cœur `aoSyncResponse` de `src/lib/ao/http.ts` : appelant vérifié, demande venue d'une page du site par `Sec-Fetch-Site`, abonnement actif côté recruteur), **jamais par une Server Action** : le navigateur exécute les Server Actions une par une, et des passages de 2 min enchaînés en arrière-plan retiendraient toutes les autres actions du site. Chaque passage renvoie les offres et e-mails à jour (`loadAoView`), affichés aussitôt sur la page AO s'ils sont plus récents que ses données (`live.version`) ; la page est rafraîchie à la fin (`router.refresh()`).
- Une seule synchronisation à la fois par organisation (cron, boutons, `ao:poll`) : verrou en base (document `lock_<empreinte>` de `ao_sync_state`, expiré après 6 min) ; un appel qui arrive pendant un passage de la même organisation est ignoré (`skipped: true`). Le bouton « Synchroniser » et « Réessayer » de `/admin/candidats` ne portent que sur les boîtes de la plateforme.
- Images (PNG, JPEG, GIF, WebP ≤ 5 Mo) et PDF sans texte (scannés) : transcrits par Claude (`claude-opus-5-5`, effort `low`, 8 000 jetons max, repli serveur sur `claude-opus-4-8` en cas de refus), 3 lectures max par e-mail et 50 par jour et par organisation (compteur dans `ao_sync_state`), clé Claude de Config IA (ou `ANTHROPIC_API_KEY`) ; sans aucune clé (ni Claude ni OpenAI), la pièce jointe est ignorée avec la raison. Archives Office vérifiées par décompression réelle bornée (50 Mo), pas d'après les tailles annoncées. Échec passager (API saturée, délai) : `RetryLater`, l'e-mail entier est repris (un report faute de temps ne compte pas comme essai).
- **Tableaux d'offres joints** (xlsx, xls, csv, tsv — tableau de suivi d'AO d'un client, export de cette page) : chaque ligne devient une offre, **sans IA** (`spreadsheet.ts`, règles pures testées avec de vrais en-têtes). Colonnes reconnues par leur nom, dans un ordre qui lève les ambiguïtés (`COLUMNS`) : intitulé (ou en-tête « Nom » seul, sauf à côté d'un prénom ou d'une vraie colonne d'intitulé : liste de personnes), client, lieu, contrat, télétravail, TJM, compétences (toutes les colonnes concernées), durée, démarrage, date limite, expérience ; description = la colonne de description telle quelle, ou une section `### <en-tête>` par colonne (contexte, missions, profil…). Les colonnes de suivi interne (numéro, statut, candidats présentés ou positionnés, notes, taux, date de réception) et celles qui nomment des personnes ou des coordonnées (interlocuteur, manager, référent, acheteur, téléphone…) sont ignorées. En-tête cherché dans les 15 premières lignes (un intitulé + au moins une autre colonne), 500 lignes et 64 colonnes lues au plus par fichier. Fichiers hostiles : contenu vérifié par ses premiers octets (une archive renommée « .xls » ou « .csv » est refusée), décompression bornée, taille annoncée par le fichier ignorée (`readSheets` avec `nodim` et bornes, dans `job-import.ts`) ; pas d'ODS (ses cellules répétées se développent sans limite à la lecture). Même validation que les réponses de l'IA (`parseOfferFields`). Au plus 500 offres de tableaux par jour et par organisation (compteur dans `ao_sync_state`) : au-delà, l'e-mail attend sans user ses essais. Un tableau aux colonnes inconnues, ou sans aucune ligne exploitable, est lu par l'IA comme texte, avec le corps de l'e-mail. Quand un tableau a été lu, le corps de l'e-mail (qui le présente) n'est pas envoyé à l'IA — il en tirerait des quasi-doublons —, les autres pièces jointes si. L'export Excel de cette page se relit à l'identique (client compris s'il est renvoyé par l'un des nôtres ; envoyé d'ailleurs, le client devient l'entreprise de l'expéditeur). Décision : `docs/adr/0003-ao-tableaux-sans-ia.md`.
- **IA indisponible, échecs sans frais** (`ai-failures.ts`, règles pures testées) : compte ou configuration (crédits épuisés, clé refusée, modèle inconnu, non configuré — côté API compatible OpenAI, seule une réponse d'erreur JSON compte) et panne du service (saturé 429/529, erreur 5xx sauf 504, injoignable). Ces requêtes sont refusées avant traitement : rien n'est facturé. Les images et PDF scannés passent alors au modèle OpenAI de Config IA (GPT-4o par défaut, clé OpenAI de Config IA ou `OPENAI_API_KEY`, `extractors/vision-openai.ts`, nom de fichier générique envoyé) ; le texte des e-mails passe déjà aux autres modèles configurés (repli de `callLLM`, qui lève `LLMChainError` avec l'échec de chacun, message inchangé ; `LLMUnreachableError` distingue « injoignable » de « sans réponse dans le délai », `LLMNotConfiguredError` un modèle non configuré). Si tous les services échouent sans frais : `AiUnavailable`, l'e-mail reste « en erreur » avec la cause par service et est repris à chaque synchronisation sans user sa reprise. Un délai dépassé ou une réponse illisible ont pu être facturés : ils suivent la règle normale (une reprise), y compris dans un échec mixte, pour qu'un e-mail ne soit pas refacturé indéfiniment. Lecture des scans impossible : le reste du passage continue, les autres e-mails à scan attendent sans nouvel appel (`PassState`). Extraction des offres impossible : le passage s'arrête. Dans les deux cas `aiUnavailable: true` dans le compte rendu (avertissement dans les logs du cron, message sur `/admin/candidats`, `ao:poll` ne relance pas plus tôt). Une lecture refusée ainsi est rendue au compteur du jour. Le courrier nouveau passe avant les e-mails à réessayer (`processingOrder`). Décision : `docs/adr/0002-repli-ia-credits-epuises.md`.
- E-mails en erreur repris **une seule fois**, au passage suivant (`MAX_ATTEMPTS = 2` dans `attempts.ts`, règle pure testée ; réponse IA tronquée ou message > 25 Mo : abandonnés tout de suite) ; un e-mail en attente de l'IA (échec sans frais, `AiUnavailable`) ou reporté faute de temps ne compte pas d'essai et revient à chaque passage. Bouton **« Réessayer »** sur chaque e-mail non traité de `/admin/candidats` (action `retryAoEmail` ; même bouton côté recruteur, `retryRecruiterAoEmail`) : remet ses essais à zéro (`manualRetryPatch`), même abandonné ou enregistré avant ces règles, **autant de fois qu'on le relance** (décision du 2026-10-26) — côté recruteur, adresse e-mail vérifiée et quota du jour : 30 relances par organisation, 300 pour toutes (`AO_RETRY_DAILY_LIMITS`, compteurs `aoRetryOrg` / `aoRetryAll`, place prise avant la remise à zéro, une relance qui échoue compte) —, puis le traite tout de suite (`syncAoEmail` : même traitement et même verrou qu'une synchronisation, sans toucher au point de reprise) ; si une synchronisation est en cours ou que ce traitement échoue, il reste en file pour la suivante. Pièces jointes zip > 50 Mo décompressées ignorées ; 50 offres max par e-mail ; données AO supprimées après 365 jours (les offres publiées restent).
- Vercel Cron ne s'exécute que sur la production ; sur une preview `dev`, utiliser le bouton « Synchroniser maintenant ». En local : `npm run dev` (ou `npm run dev:local` si Appwrite répond en « fetch failed (ETIMEDOUT) » : réseau sans IPv6 / serveur à plus de 250 ms) puis `npm run ao:poll` (même appel toutes les `AO_POLL_INTERVAL_MINUTES` minutes, 5 par défaut, ou `--every N` ; `--once` pour un seul passage ; en arrière-plan : `npm run ao:poll:start` / `ao:poll:status` / `ao:poll:stop` ; `CRON_SECRET` ≥ 16 caractères dans les fichiers .env lus par `next dev`). Hors Vercel, n'importe quel planificateur peut appeler `GET /api/cron/ao-inbox` avec `Authorization: Bearer $CRON_SECRET`.
- Variables : `AO_CREDENTIALS_KEY` (32 octets base64, serveur seulement ; la changer rend les mots de passe enregistrés illisibles), `APPWRITE_COLLECTION_AO_EMAILS` / `_AO_OFFERS` / `_AO_STATE` / `_AO_SOURCES`, `CRON_SECRET` (≥ 16 caractères), `AO_IMAP_*` (lues seulement par `ao:migrate-sources`) — voir `.env.example`.
- Tests : `npm test` (node:test + tsx, fichiers `src/**/*.test.ts`) ; `npm run typecheck`.

# Assistant IA (module portable)

- **Module `src/assistant/`** (ADR 0007, guide d'intégration `src/assistant/README.md`) : n'importe rien de l'application (règle ESLint) ; le cœur (`core/`) ne dépend d'aucun framework, la fenêtre (`react/`) pas de Next.js. Le site fournit ses adaptateurs `AssistantHost` : pour MyBestConsultant `src/lib/assistant/host.ts` (`server-only`), actions `src/lib/assistant-actions.ts`, fenêtre `src/components/assistant/mbc-assistant.tsx` dans les layouts candidat et recruteur, variables de style `.mbc-assistant` dans `globals.css`.
- **Périmètre v1** : candidats et recruteurs connectés **à l'adresse e-mail vérifiée** (inscription libre : sinon des comptes jetables épuiseraient le quota de la plateforme) ; réponses tirées seulement de `src/lib/assistant/knowledge.ts` (à mettre à jour quand une page, un libellé ou une règle change), aucun accès aux données de l'utilisateur, aucun outil. « Transmettre au support » crée un ticket du Help Desk avec la conversation (après confirmation ; limite de 10 demandes ouvertes inchangée ; lignes suivantes d'un message préfixées « › » pour qu'un utilisateur ne puisse pas écrire une fausse réponse « Assistant : »). La conversation transmise suit ensuite la conservation du Help Desk (sans règle de suppression à ce jour).
- **Modèle** : ligne « Assistant IA » de Config IA, **sans repli** (`callLLM` avec `strict: true`) pour que les conversations n'aillent qu'au modèle choisi. En mode strict, `callLLM` refuse aussi l'appel quand Config IA est illisible ou quand le modèle choisi a été retiré ou désactivé (`LLMNotConfiguredError`) ; panne = message d'erreur. Par défaut : le modèle par défaut de Config IA.
- **Quotas** (`takeDailySlot`, compteurs `assistantUser` / `assistantAll` dans AO_STATE) : 30 messages par utilisateur et par jour (UTC), 1 000 pour la plateforme (`ASSISTANT_DAILY_LIMITS` ; message distinct et avertissement dans les journaux quand la plateforme est au plafond). Un message refusé par une panne du modèle compte quand même. Message de 2 000 caractères au plus, 10 derniers échanges et 12 000 caractères d'historique envoyés au modèle, réponse coupée à 8 000 caractères sans couper un emoji (`src/assistant/core/rules.ts`, testé).
- **Données** : collection `assistant_turns` (5/16 attributs, sans permission client), un document par échange, enregistré seulement après la réponse (enregistrement impossible : réponse affichée avec un avertissement, non reprise) ; toute lecture filtre sur l'utilisateur de la session (conversation d'un autre = « introuvable »). Supprimés après **30 jours** (`ASSISTANT_RETENTION_DAYS`, décision du 2026-10-23 ; durée annoncée dans la fenêtre et dans le contenu d'aide) par `/api/cron/assistant-purge` (Vercel Cron, quotidien, 5 min au plus ; purge aussi les places de quota de plus de 7 jours) et avec le compte : `deleteUserAccount` (avant le compte, puis second passage après) et `removeMember` (retrait d'un membre d'équipe).
- **Deux variables** : `APPWRITE_COLLECTION_ASSISTANT_TURNS` (collection : la purge et la suppression avec le compte en dépendent, **ne pas la retirer** tant qu'elle contient des conversations) et `ASSISTANT_ENABLED=true` (affiche l'assistant ; le masquer = retirer celle-ci).
- **Mise en place** : `npm run assistant:setup -- .env.dev` (simulation), puis `--apply` sur DEV ; variables en portée **Preview** de Vercel et dans un fichier local qui vise `bestconsultant-dev`, test sur la preview `pre-dev`. Production : un humain sauvegarde la base, lance `--prod` puis `--prod --apply`, et seulement ensuite définit les variables en portée Production et redéploie (variable définie sans collection : l'assistant échoue). Retour arrière complet : exporter si besoin, puis supprimer la collection dans la même opération que le retrait de la variable ou du code.
- Tests : `src/assistant/core/*.test.ts` (site fictif : refus d'un visiteur, d'une conversation d'un autre, d'une saisie invalide, quotas de l'utilisateur et du site, panne et réponse vide du modèle sans rien enregistrer, enregistrement impossible après la réponse, fausse ligne « Assistant : » dans la transcription).

# Export des CV au format ESN

- **« Format ESN »** dans `/admin/cvtheque` (admin seulement, ADR 0009) : dossier de compétences anonymisé d'un candidat dans le template Wise Associates, en Word, français et/ou anglais (`.zip` pour les deux), anonymisation standard ou renforcée (clients et employeurs remplacés). Fenêtre `esn-export-dialog.tsx` ; route `POST /api/admin/cv-export/[candidateId]` (vérifie elle-même le rôle admin ; candidats de rôle `candidate` seulement ; `maxDuration = 300`) ; compte rendu (champs « [À COMPLÉTER] », contenus non repris) dans l'en-tête `X-Cv-Export-Notes`. Génération : 1 à 3 min d'IA, puis enregistrement (ci-dessous).
- **Modèle CV** (ADR 0010, décision du 2026-10-24) : chaque organisation dépose le sien **depuis sa CV Thèque** (bouton « Modèle CV » de l'en-tête, `src/components/cv-export/cv-template-manager.tsx`, le même dans les deux CV Thèques) : .docx + `template_map.json` de la skill, vérifiés par `checkTemplate` qui rend un candidat fictif en FR et EN (`template-upload.ts`, `server-only`, partagé par les actions des deux pages). `/recruiter/cvtheque` : **tout recruteur** de l'organisation dépose, remplace ou retire (organisation de la session), à l'adresse e-mail vérifiée, 20 dépôts et 30 aperçus par jour et par organisation (`CV_TEMPLATE_DAILY_LIMITS`, compteurs `cvTemplateOrg` / `cvTemplatePreview` : chaque rendu d'un modèle déposé par un recruteur passe par un quota). Modèle = contenu non fiable rendu sur le serveur : archive vérifiée par `zipFitsWithin` (tailles réelles égales aux tailles annoncées, nombres d'entrées concordants, pas de zip64), parties XML de 5 Mo au plus, structure bornée à 20 000 éléments et 500 enfants sous un même élément (`assertBoundedStructure`, `render.ts` : xmldom réindexe les frères à chaque retrait, des paragraphes vides en grand nombre bloquaient le serveur) ; les exports perdent le modèle Word d'origine (`attachedTemplate`, chemin avec un nom de session Windows). `/admin/cvtheque` : l'admin dépose le modèle de la plateforme (« admin ») ; sans modèle déposé, celui de Wise Associates du dépôt (retirer = y revenir). Admin → Entreprises ne gère plus les modèles (liste réservée au super-admin). Aperçu fictif téléchargeable (`/api/admin/cv-templates/sample`, `/api/recruiter/cv-templates/sample`) ; exemple pour préparer un modèle (`…/cv-templates/example`) : `templates/example/`, copie du modèle Wise dont le bloc contact (nom, téléphone, e-mail d'un commercial) est remplacé par des valeurs fictives, testée (aucune trace de ce contact) — ne jamais servir `templates/wise-associates/` aux recruteurs. Fichiers inclus par `outputFileTracingIncludes`.
- **Recruteurs** (ADR 0010) : « Format ESN » aussi dans `/recruiter/cvtheque`, dans le **modèle de leur organisation**. Sans modèle : pas de bouton sur les candidats, seulement « Ajouter votre modèle CV » ; sans les variables `CV_TEMPLATES` : ni l'un ni l'autre. Route `/api/recruiter/cv-export/[candidateId]` (organisation de la session, jamais de la requête) ; générer exige abonnement `active` / `trialing`, adresse e-mail vérifiée et quota du jour (20 par organisation, 300 pour toutes : `CV_EXPORT_DAILY_LIMITS`, compteurs `cvExportOrg` / `cvExportAll`, règles pures `access.ts`, testées) ; retélécharger une version enregistrée est libre. Places de quota prises juste avant l'IA et rendues si elle refuse sans frais (`takeDailySlotId` / `releaseDailySlot`, `state.ts`) ; modèle revérifié (`checkTemplate`) avant chaque génération, juste avant l'IA et après la prise des places (rendues si le modèle est inutilisable) ; 2 Mo au plus par modèle (`limits.ts` : un .zip FR + EN doit tenir sous les 4,5 Mo des réponses Vercel), taille décompressée annoncée bornée à 50 Mo (`unzipTemplate`, `render.ts`) ; version antérieure au modèle actuel signalée (`stale: 'template'`). Modèles : collection et bucket `cv_templates` (document d'identifiant celui de l'organisation, « admin » pour la plateforme ; `templates.ts`, `server-only`). Cœur des routes (session admin / recruteur, export, téléchargements du modèle) : `http.ts` ; fenêtre partagée : `src/components/cv-export/esn-export-dialog.tsx` (route, lecture des versions et refus de générer passés en props) ; état côté recruteur : `recruiter.ts`.
- Code dans `src/lib/cv-export/` : `render.ts` = portage TypeScript de `render_cv.py` de la skill `cv-esn-anonymise` (même `template_map.json` ; à garder aligné sur le script Python), `leak-check.ts` (partie « fuites » de `check_cv.py` : nom aussi collé ou coupé de caractères invisibles, téléphone connu comparé sur ses chiffres, tout autre e-mail ou téléphone, tout lien absent du template, auteurs ; ce qui figure déjà dans le template vierge est à l'ESN ; une fuite **bloque** l'export), `cv-data.ts` (validation **stricte** des réponses de l'IA : rubrique absente ou d'un autre type, langue inconnue ou termes d'identité absents = réponse refusée, jamais une rubrique perdue ni un texte coupé ; réponse tronquée ; traduction de même structure, champs remplis compris (`structureGap`) ; initiales, noms de fichiers, certifications versées dans la Formation quand le template n'a pas de rubrique), `prompt.ts`, `export.ts` (`server-only`, orchestration). Template et cartographie : `templates/wise-associates/` (copiés de la skill), inclus dans la fonction Vercel par `outputFileTracingIncludes` (`next.config.ts`). La pagination de `check_cv.py` (LibreOffice) n'est pas portée : relire le document dans Word.
- **IA** : ligne « Export CV (format ESN) » de Config IA, **sans repli** (`callLLM` strict : le CV ne part que chez ce modèle), `maxTokens` 16 000, délais 140 s (extraction) et 120 s (traduction), sans nouvel essai, le tout fini 265 s après le début. Sans modèle choisi : modèle par défaut de Config IA ; Claude Sonnet recommandé (extraction et traduction fidèles ; un modèle local à contexte court coupe un long CV sans prévenir). Génération (POST) acceptée seulement depuis une page du site (`Sec-Fetch-Site`).
- **Versions enregistrées** (décision du 2026-10-23, ADR 0009) : la **dernière** version de chaque candidat × anonymisation × langue est gardée (collection `cv_exports`, 9/16 attributs, une version **par organisation** (`tenantId`, « admin » pour la plateforme), index unique `candidateId` + `tenantId` + `mode` + `lang` ; bucket privé `cv_exports`, .docx chiffrés ; aucune permission client), remplacée à chaque génération, **supprimée avec le compte** du candidat (`deleteUserAccount` : avant le compte, l'échec bloque la suppression ; second passage après), sans autre durée de conservation. La fenêtre lit les versions (`getCvExportVersions`, sans fichier ni identifiant) : version présente pour le choix → « Télécharger » (`GET /api/admin/cv-export/[candidateId]?mode=…&lang=…`, aucun appel d'IA) et « Générer une nouvelle version » (POST) ; version tirée d'un CV remplacé depuis (`sourceCvFileId` ≠ CV actuel) : signalée, l'action principale devient « Générer une nouvelle version ». Enregistrement impossible après une génération : le fichier est quand même livré, la fenêtre le signale (`X-Cv-Export-Saved: failed`). Code : `store.ts` (`server-only`, Appwrite), `stored.ts` (règles pures, testées). Fichiers du bucket nommés `<candidat>_<mode>_<langue>.docx` (le nom téléchargé est dans le document) : la suppression avec le compte retrouve aussi par ce nom un fichier qu'aucun document ne référence plus (deux générations simultanées). Facultatif : sans `APPWRITE_COLLECTION_CV_EXPORTS` et `APPWRITE_STORAGE_CV_EXPORTS`, rien n'est enregistré et la fenêtre le dit. **Mise en place** (ADR 0010, en deux temps) : `npm run cv-export:setup -- .env.dev` (simulation), `--apply` sur DEV (crée `cv_templates`, ajoute `tenantId`, rattache les versions existantes à « admin », crée le nouvel index unique, **garde** l'ancien `candidateversion`), déployer, puis `--apply --drop-old-index` (rattache les versions écrites entre-temps, supprime l'ancien index) ; seulement alors `APPWRITE_COLLECTION_CV_TEMPLATES` / `APPWRITE_STORAGE_CV_TEMPLATES` en portée Preview. **Ne jamais revenir sur le code après la migration** (l'ancien code écraserait la version d'une autre organisation) : pour couper la fonction côté recruteurs, retirer les variables `CV_TEMPLATES`. Production (un humain ; ADR 0009 et 0010 ensemble) : déployer le code sans les variables (sans effet), sauvegarder la base, `--prod` puis `--prod --apply` (relancer s'il s'arrête en route), relancer `--prod` : aucune ligne « + », « Rien n'a été modifié. » ; seulement alors définir les **quatre** variables (`CV_EXPORTS` et `CV_TEMPLATES`), en portée Production seulement, et redéployer. Variables définies avant la structure : toute suppression de compte est refusée (message « stockage … introuvable »). Le script vérifie aussi une collection ou un bucket déjà présents (permissions, chiffrement, index unique). **Retour arrière** : ne jamais retirer les variables ni revenir sur le code tant que le bucket contient des exports (la suppression avec le compte en dépend) ; soit masquer seulement le bouton, soit supprimer bucket et collection (exports régénérables depuis le CV d'origine) dans la même opération que le retrait des variables.

# Vivier général des recruteurs (matching automatique)

- **`/recruiter/vivier`** (décision du 2026-10-28) : en plus du vivier de chaque offre (inchangé, `/recruiter/vivier/[jobId]`), un **vivier général** où le recruteur dépose des CV sans choisir d'offre. Même import (navigateur → bucket `VIVIER_CVS`, puis `attachVivierCv(null, …)`), mais dans une fenêtre (« Importer des CV », demande du 2026-10-28 : la zone de dépôt ne doit pas repousser la liste des offres ; l'import continue fenêtre fermée). La page a deux onglets, « Viviers par offre » (vue par défaut) et « Vivier général » (`vivier-tabs.tsx`, même demande) : une vue à la fois, l'autre masquée mais montée (import et synchronisation continuent), vivier général gardé dans l'adresse (`?vue=general`), même confidentialité (CV visibles de celui qui les a importés ; tous ceux de l'organisation pour un admin), mêmes fiches. Un CV du vivier général est un document `vivier_cvs` **sans `jobId`** (`Query.isNull('jobId')`) ; `matchScore` / `matchReason` y restent vides (ils sont ceux du vivier d'une offre). Les lectures plafonnées des viviers d'offres (tableau de bord, annonces, reporting, compteurs de `/recruiter/vivier`) excluent le vivier général (`Query.isNotNull('jobId')`) : un import massif les remplirait. **Fichier envoyé par le navigateur** (bucket sans session, donc sans propriétaire) : `attachVivierCv` n'accepte qu'un fichier envoyé depuis 15 minutes au plus et rattaché à aucun CV (`assertFreshUpload`, index `cvFileId_idx`) ; « Supprimer » garde un fichier encore rattaché à un autre CV. CV ou offre d'un autre = « introuvable », comme s'ils n'existaient pas. « Analyser à nouveau » est refusé pour un CV déjà analysé.
- **Matching automatique** : après la création du profil, le CV est comparé par l'IA aux **offres ouvertes de l'organisation** (`getOpenJobsOfTenant` : actives, non expirées, sans celles de la plateforme), 15 offres par appel en parallèle, les 100 plus récentes (toutes celles que lit `getOpenJobsOfTenant`, pour qu'un CV qui correspond déjà à une offre ait été comparé à toutes les autres). Seul le parcours professionnel part à l'IA (postes, compétences, résumé, années, langues), **jamais le nom ni les coordonnées**, chaque champ borné (une offre aux centaines de compétences ne fait pas un appel de la taille du contexte, testé). Modèle : celui du « Matching IA » de Config IA, ou **Claude** s'il n'y en a pas (`callLLM` option `moduleDefault`, `pickPrimary` testé), repli habituel s'il échoue. Un CV **correspond** à une offre notée 65 ou plus (`SOURCING_MIN_SCORE`). Scores enregistrés sur le CV, attribut `offerMatchesJson` (JSON : offre, score, raison pour les 10 meilleures ; offres fermées retirées à chaque écriture) ; relu juste avant l'écriture, ce qui réduit à quelques millisecondes la fenêtre où deux comparaisons simultanées du même CV s'effacent (les offres perdues redeviennent « nouvelles »). Règles pures : `src/lib/vivier-matching.ts` (testé) ; appel : `scoreCvAgainstOffers` (`matching-core.ts`) ; actions : `src/app/recruiter/vivier/actions.ts` (partagées par les deux pages, organisation et propriétaire du CV vérifiés à chaque action par `ownVivierDoc`).
- **« Sans offre correspondante »** (bouton et fenêtre `unmatched-cvs.tsx`) : CV au profil créé sans aucune offre ouverte à 65 ou plus, avec le nombre d'offres ouvertes jamais comparées ; « Synchroniser » compare chacun, l'un après l'autre (`syncVivierCvMatching`), aux seules offres nouvelles pour lui ; « Arrêter » après le CV en cours ; arrêt au premier refus ou échec (appel interrompu compris). Les nouvelles offres ne sont pas comparées automatiquement aux CV existants, ni par « Synchroniser » aux CV qui correspondent déjà à une offre (demande du 2026-10-28 : synchronisation à la main, des CV sans correspondance). Un lot en échec sur un CV qui correspond déjà à une offre laisse ces offres non comparées (message distinct, `partial`). Les actions du vivier général ne relisent pas la page (`revalidateVivier`) : la liste vit dans l'état du client, qui se met à jour.
- **Coût** : chaque comparaison d'un CV (quel que soit le nombre d'offres) exige l'adresse e-mail vérifiée et prend une place sur les quotas du jour : 200 par organisation, 2 000 pour toutes (`VIVIER_MATCHING_DAILY_LIMITS`, compteurs `vivierMatchOrg` / `vivierMatchAll` dans AO_STATE, purgés avec les autres) ; une comparaison qui échoue compte. Refus et échec : le CV est importé quand même et le message s'affiche ; sans offre correspondante, il apparaît dans « Sans offre correspondante ». `takeDailySlotId` refuse sans écriture quand toutes les places du jour sont prises.
- **Mise en place** : attribut `offerMatchesJson` (texte, 20 000) et index `cvFileId_idx` de `vivier_cvs` (12/16 attributs), dans `appwrite.config.json` : `npm run schema:push -- dev` avant de déployer sur la preview ; production : `schema:check -- prod` puis `schema:push -- prod` **par un humain** avant la mise en production. Sans l'attribut, l'import dans le vivier général réussit mais chaque comparaison échoue après l'appel à l'IA (message « La comparaison aux offres n'a pas abouti », « Unknown attribute » dans les journaux).
- Tests : `src/lib/vivier-matching.test.ts`, `src/lib/ai/models.test.ts`.

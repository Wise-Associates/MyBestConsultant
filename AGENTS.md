# Behavioral Guidelines (Andrej Karpathy)

Behavioral guidelines to reduce common LLM coding mistakes.

**Tradeoff:** These guidelines bias toward caution over speed. For trivial tasks, use judgment.

## 1. Think Before Coding

**Don't assume. Don't hide confusion. Surface tradeoffs.**

Before implementing:
- State your assumptions explicitly. If uncertain, ask.
- If multiple interpretations exist, present them — don't pick silently.
- If a simpler approach exists, say so. Push back when warranted.
- If something is unclear, stop. Name what's confusing. Ask.

## 2. Simplicity First

**Minimum code that solves the problem. Nothing speculative.**

- No features beyond what was asked.
- No abstractions for single-use code.
- No "flexibility" or "configurability" that wasn't requested.
- No error handling for impossible scenarios.
- If you write 200 lines and it could be 50, rewrite it.

Ask yourself: "Would a senior engineer say this is overcomplicated?" If yes, simplify.

## 3. Surgical Changes

**Touch only what you must. Clean up only your own mess.**

When editing existing code:
- Don't "improve" adjacent code, comments, or formatting.
- Don't refactor things that aren't broken.
- Match existing style, even if you'd do it differently.
- If you notice unrelated dead code, mention it — don't delete it.

When your changes create orphans:
- Remove imports/variables/functions that YOUR changes made unused.
- Don't remove pre-existing dead code unless asked.

The test: Every changed line should trace directly to the user's request.

## 4. Goal-Driven Execution

**Define success criteria. Loop until verified.**

Transform tasks into verifiable goals:
- "Add validation" → "Write tests for invalid inputs, then make them pass"
- "Fix the bug" → "Write a test that reproduces it, then make it pass"
- "Refactor X" → "Ensure tests pass before and after"

For multi-step tasks, state a brief plan:
```
1. [Step] → verify: [check]
2. [Step] → verify: [check]
3. [Step] → verify: [check]
```

Strong success criteria let you loop independently. Weak criteria ("make it work") require constant clarification.

# High-Agency Frontend Architect Principles

Core principles for production-quality frontend decisions on this project.

## Architecture

- **Route structure is URL structure.** Flat paths (`/candidate/dashboard`) not route groups for namespacing.
- **Server Components by default.** Only add `'use client'` when you need state, events, or browser APIs.
- **Data at the edge.** Fetch in Server Components, pass down as props. Never fetch in client components unless real-time.
- **CSS variables over Tailwind tokens** for any themeable value — colors, fonts, radius, shadows.

## Component Design

- **No premature abstraction.** Three similar components is better than one wrong abstraction.
- **Props over context** for component-local state. Context for cross-tree global state (auth, theme).
- **Forms via Server Actions.** No client-side fetch for mutations — use `useTransition` + server action.
- **Loading states always.** Every async action has a pending state. Never leave the user guessing.

## TypeScript

- **Strict mode.** No `any`, no non-null assertions without a comment explaining why.
- **Union types for variants.** `type Status = 'pending' | 'ok' | 'error'` not magic strings scattered in the code.
- **Interface for external shapes** (API responses, Appwrite documents). Type for internal unions/compositions.

- **Weight inversion**: H1 weight 300 (elegant), H2 weight 700 (structural). Don't flip this.

## Appwrite (Self-hosted 1.7.4)

- **No underscores in labels.** Use `admin` not `super_admin`.
- **node-appwrite v15** — don't upgrade, server is 1.7.4.
- **Connexions gardées ouvertes** (2026-10-30) : `createAdminClient`, `createSessionClient` et `createGuestClient` (`src/lib/appwrite/client.ts`) utilisent `KeepAliveClient`, qui partage une connexion par serveur Appwrite. node-appwrite 15 en ouvrait une nouvelle à chaque appel (poignées de main TCP et TLS) : ~750 ms par appel depuis un poste éloigné, ~255 ms en la réutilisant (mesuré sur DEV). Toujours passer par ces fonctions, jamais `new Client()` ; dépendance directe `node-fetch-native-with-agent` épinglée à la version qu'utilise node-appwrite.
- **Cookies**: `mbc-session` (httpOnly) + `mbc-role` (readable by middleware). Never rename.
- **Server Actions** call `createAdminClient()` not `createSessionClient()` for mutations.
- **Sign-up never joins an existing organisation**: a recruiter who registers always gets a new tenant (unique slug `nom`, `nom-2`… via `src/lib/tenant-slug.ts`); colleagues join only through an invitation (`src/lib/team.ts`, `/recruiter/equipe`). Typing a company's name must never give access to its data.
- **Every admin Server Action and `/api/admin/*` route checks the caller itself** (`requireAdmin()` from `@/lib/appwrite/auth`, or role check → 401/403). Server Actions are public POST endpoints: the admin layout only guards page rendering. Code outside `src/app/admin` never imports admin actions; shared reads live in `src/lib`.
- **Collection attribute limit: 16.** Count before creating new attributes.
- **Emails d'Appwrite** (vérification de l'adresse, mot de passe oublié) : en 1.7.4, le serveur refuse tout envoi (« SMTP Disabled », `general_smtp_disabled`, 503) tant que la variable `_APP_SMTP_HOST` de son `.env` est vide, **même si le SMTP du projet est activé dans la console** (ce réglage ne choisit que le serveur et l'expéditeur une fois ce contrôle passé). Après modification du `.env` du serveur : `docker compose up -d` (un `restart` ne relit pas le fichier). L'URL de retour (`NEXT_PUBLIC_APP_URL` + `/verify-email/confirm` ou `/reset-password`) doit avoir pour hôte une **plateforme Web du projet** (console → Overview → Platforms : `localhost`, domaine de preview, domaine de prod), sinon 400 `general_argument_invalid` ; pas de joker `*.ngrok-free.app` (n'importe qui pourrait faire pointer un lien de réinitialisation vers son propre tunnel). Message montré à l'utilisateur : `translateAuthError` (`src/lib/appwrite/auth-errors.ts`, testé) ; cause dans les journaux (`[verify-email]`, `[auth]`).

# Git & Deploy Workflow

- **Work on `pre-dev` only.** One change per commit with a clear message, then `git push origin pre-dev`. Vercel deploys `pre-dev` as the preview wired to the DEV Appwrite project (`bestconsultant-dev`).
- **Never touch production.** No push to `prod`, `main` or any other branch, no force push, no `vercel --prod` / `deploy` / `promote` / `rollback` / `env` / `alias` — a hook in `.claude/settings.json` blocks them. Production is released by a human through a pull request `dev` → `prod`.
- **Undo with `git revert <sha>` then `git push origin pre-dev`.** Never rewrite pushed history (`reset --hard` + force push).
- **Never read or print `.env*` files.** Scripts may load them; you don't.
- **Verify after pushing.** Wait for the preview (`vercel ls`, `vercel inspect <url> --logs`), then check the page in the browser.

Workflow en deux jobs : `verify` (code et dépendances, sans secret) puis `deploy` (clé SSH, aucun code du dépôt hors du build Docker) ; ne pas y ajouter d'étape qui exécute le code du dépôt.
- **Nouvelle variable d'environnement** : aussi dans `/etc/mybestconsultant/app.env` sur le serveur, avant la mise en production du code qui la lit (un humain) ; une `NEXT_PUBLIC_*` aussi dans les variables de l'environnement GitHub `production` (écrites dans l'image au build).
- Fichier lu sur disque à l'exécution : à déclarer dans `outputFileTracingIncludes` (`next.config.ts`), sinon absent de l'image comme des fonctions Vercel. Écriture sur disque : `/tmp` seulement (conteneur en lecture seule).
- **Aucune page générée au build avec des données** : le build de l'image n'a que les `NEXT_PUBLIC_*`. Layout racine et `sitemap.ts` en `dynamic = 'force-dynamic'` ; `scripts/check-prerendered.mjs` (lancé par le Dockerfile) fait échouer le build sinon. Une nouvelle route de métadonnées qui lit Appwrite (opengraph, manifest…) prend la même option.
- Après la bascule, Vercel Cron est désactivé et les tâches passent par `deploy/crontab` (mêmes heures) ; les mentions de Vercel Cron plus bas sont à remplacer à la sortie de Vercel (étape 7 du guide).

# Structure Appwrite (appwrite.config.json)

- **`appwrite.config.json` = structure du projet DEV** (collections, attributs, index de la base `bestconsultant-dev`, et buckets du projet : ADR 0017), versionnée, appliquée par la CLI Appwrite épinglée (`appwrite-cli` **8.3.0**, la dernière pour le serveur 1.7.x : ne pas la monter) ; décision : `docs/adr/0011-structure-appwrite-appwrite-config.md`. Ne jamais le réécrire avec un outil qui lit les nombres en double précision (bornes ±9223372036854775807 arrondies) : `npm run schema:pull` ou une édition à la main.
- Session : `npm run appwrite -- login --endpoint https://appwrite.mybestconsultant.fr/v1`, puis `npm run appwrite -- logout` (session de la console : tous les projets, production comprise).
- `npm run schema:pull` (remplace le fichier par la structure de DEV) ; `npm run schema:check -- dev|prod` (lecture seule, code 1 s'il diffère) ; `npm run schema:push -- dev|prod` : **ajouts seulement** (collection — permissions affichées —, attribut facultatif, index non unique) et **ne supprime jamais** (ce que seul le projet a est gardé, ligne « · », la CLI reçoit le fichier complété) ; refuse (lignes « ✗ », rien n'est poussé) recréation (type, taille…), attribut obligatoire ou index unique ajoutés à une collection existante, modification sur place (obligatoire, valeur par défaut, bornes, énumération) et réglages de collection (permissions, `documentSecurity`) — la CLI 8.3.0 affiche ces deux derniers mais ne les applique pas —, index du projet non disponible (« failed »), bornes arrondies ; confirmation en tapant l'identifiant du projet, comparaison refaite juste après, jamais `--force`, structure relue après (même si la CLI échoue) ; sur DEV, fichier repris depuis le projet après un push réussi (réglages par défaut d'un attribut écrit à la main). Règles pures : `src/lib/appwrite/schema-diff.ts` (testé) ; script : `scripts/appwrite-schema.mts` (copie du fichier dans un dossier temporaire : la base de production est `bestconsult`, pas `bestconsultant-dev`).
- **Ajouter** une collection, un attribut ou un index : DEV d'abord (console puis `schema:pull`, ou fichier puis `schema:push -- dev`), commit du fichier avec le code ; production : `schema:check -- prod`, puis `schema:push -- prod` **par un humain**, après sauvegarde de la base, avant la mise en production du code qui l'utilise.
- **Buckets** (ADR 0017, décision du 2026-10-29) : `schema:pull` lit tous les buckets de DEV ; `schema:push` **crée seulement** ceux qui manquent au projet (la CLI ne reçoit qu'eux : sur un bucket existant, `push bucket` réécrirait tous ses réglages, permissions comprises). Un bucket existant qui diffère du fichier est signalé (ligne « ! », `schema:check` et `schema:push` répondent 1), **jamais modifié**, sans bloquer les autres ajouts : à corriger dans la console avant de s'en servir. Si la CLI affiche un tableau de modifications pour un bucket pendant `schema:push`, répondre NO (bucket créé entre-temps). Règles pures `diffBuckets`, `pushCopy`, `needsAttention` (`schema-diff.ts`, testées).
- **Reste un script** (avec simulation, `--apply`, `--prod`) ou la console : données (remplissage, rattachement), suppressions et changements de type (nouvel attribut, migration, suppression de l'ancien après le déploiement), modifications d'un attribut existant (le rendre obligatoire une fois rempli…), index unique sur une collection qui a des données (doublons vérifiés ; remplacement en deux temps), réglages d'un bucket existant, réglages de collection. Après un script de structure ou une modification dans la console de DEV, `schema:pull` puis `schema:check -- prod`.

Montant selon le contrat (annuel brut pour CDI / CDD, salaire mensuel × 12 ; TJM sinon ; `null` si l'unité est inconnue). **Un stage n'est jamais un CDI ni un CDD** : `mission`, sans montant (la gratification, mensuelle, s'afficherait en €/j), « Stage » gardé dans le titre — garanti par le code d'après le titre (`withInternshipTerms`, `parse.ts`, testé : « stage », « stagiaire », « internship », « intern » ; « stages » au pluriel non, c'est souvent un vrai poste). Pas de valeur « Stage » dans les contrats : elle toucherait `ao_offers` et `jobs` et toutes les listes de libellés.
- **Offres de la veille (scraping)** (ADR 0008) : le projet `veille-marches-emplois` (appels d'offres BOAMP / TED et offres d'emploi d'organismes publics) envoie chaque offre relevée dans son propre e-mail à la boîte AO, avec l'en-tête `X-Wise-Veille: scraping`, depuis une adresse de nos domaines. Même traitement qu'un autre e-mail (IA, dédoublonnage par empreinte, « à valider »), avec trois différences : e-mail reconnu par `fromVeille` (`origin.ts`, testé : en-tête **et** expéditeur d'un de nos domaines exacts ou sous-domaine, boîte de la plateforme seulement, sinon e-mail ordinaire) ; offre dont la date limite, désignée comme telle par le texte (`deadlineFromText`), est déjà passée écartée (`isPastDeadline`, `dates.ts`, testé ; noté sur l'e-mail) — pour la veille seulement, la date limite des autres e-mails pouvant être déduite d'une date sans libellé ; canal enregistré dans `ao_offer_details.channel` (« scraping » ; absent = e-mail), affiché dans la colonne « Source » (`AO_CHANNEL_LABEL`, `filters.ts`). La colonne n'affiche plus le nombre d'e-mails d'une offre (`sourceCount`, toujours dans la carte « Doublons fusionnés » et le panneau). **Mise en place** : `npm run ao:setup -- <env> --apply` (attribut `channel`) avant de déployer ce code sur un projet.
- Les offres arrivent « à valider ». Un admin publie une copie anonymisée : client (variantes du nom, sigle) et expéditeurs (celui de l'e-mail et celui du message d'origine) remplacés par un libellé générique, coordonnées et références d'appel d'offres (`REFERENCE_CODE` : « RFC00094023 », « DH038970 », numéros de la veille — avis BOAMP « 26-105130 », TED « 654321-2026 » et « 2023/S 123-456789 », offres Choisir le service public « 2026-2442607 », « MEF_2026-33005 » ; normes même datées, versions, dates et fourchettes de montants exclues, « ISO27001 », « ISO 27001-2022 », « AX2012 », « 2026-01-15 », « 45-550000 € » ; `name-match.ts`) retirées, dans le titre, la description, la ville et les compétences ; règles réappliquées côté serveur. Leur libellé part avec elles en début de ligne ou entre parenthèses (« Réf. TED : … », « (référence : …) », « Avis BOAMP n° … », titre « ### Référence BOAMP » dont le numéro est dessous), pas dans une phrase (« indiquez la référence DH038970 » garde « la référence ») ; un titre « ### Référence » sans numéro et « Références » restent. Un nom masqué après un article élidé ou féminin devient « le / du / au / un / ce client confidentiel » (« L'ENSMIS » → « Le client confidentiel », « la SNCF » → « le client confidentiel », jamais « L'Client confidentiel »), quelle que soit l'entreprise affichée ; les articles masculins restent devant l'entreprise affichée ; « X (X) » après masquage (sigle et nom complet) devient « X » (`scrubContacts`, `anonymize.ts`, testé). L'offre publique a l'identifiant fixe `ao<id de l'offre AO>` (pas de double publication). La page admin et l'export Excel gardent les vraies données (usage interne). **Publication** (`publishAoOfferOf`, même code pour l'admin et les recruteurs ; offre publique rattachée à `tenantId = "admin"` pour les boîtes de la plateforme, à l'organisation sinon) : la requête ne crée que l'offre publique et répond en quelques secondes ; la diffusion sur les réseaux (`tryAutoPublishJob`, échéance `deliveryDeadline` du début de la requête ; seulement si « Publication automatique » est activée dans `/admin/social`, sinon ancien auto-post LinkedIn) et le sourcing automatique partent en parallèle après la réponse (`after()`, dans les 300 s de la page) : attendu, le sourcing ferait patienter « Publier » environ 3 min.
- **« Préparer la publication »** (ADR 0013, décision du 2026-10-27) : l'IA de Config IA (modèle par défaut, avec repli) rédige une version **totalement anonyme et mise en forme** à partir de l'offre déjà nettoyée : intitulé sans client ni référence, entreprise affichée = secteur générique (« Grand groupe bancaire »), accroche, `### Au programme`, `### Profil recherché`, `### Modalités` en puces, en français, sans emoji (les emojis restent dans les publications sociales, `social-content.ts`). Prompt, validation stricte de la réponse et mise en forme : `src/lib/ao/publication-copy.ts` (pur, testé) ; appel : `rewriteForPublication` (`offer-actions.ts`), 60 s par modèle. Les noms que l'IA dit avoir retirés (`maskTerms`, même laissés par erreur dans sa version, sauf la ville de l'offre) sont signalés à la relecture et masqués à la publication, chacun tel quel (`maskNames`, sans les variantes de `namesToHide` : « Group IT » ne masque pas « IT ») et après les noms connus. L'entreprise affichée n'est retenue que sans nom à masquer, coordonnée ni référence (`publicLabel`), sinon « Client confidentiel ». IA refusée ou en échec : version des règles automatiques (`descriptionForPublication`), avec la raison affichée. **Validation humaine obligatoire** : le panneau montre le formulaire à côté de l'aperçu de l'offre publiée, liste les noms du client masqués à la publication (`maskedNames` : clients cités, autres noms et, version de l'IA, `maskTerms` ; sans aucun, avertissement : les règles ne reconnaissent que ces noms), signale en rouge les noms et références encore présents (`findIdentifiers`, `name-match.ts`, pur et utilisable dans le navigateur), et « Publier » exige la case « J'ai relu… », décochée par toute modification ; le serveur refuse une publication sans `reviewed: true`. Préparation (≈ 30 s) et publication (création, diffusion, sourcing : une minute ou plus) sont tenues par la section AO et non par la page de l'offre (`AoPublicationsProvider`, `src/components/ao/offer-publications.tsx`, monté par `src/app/admin/candidats/layout.tsx` et `src/app/recruiter/parametres/boites-ao/layout.tsx`) : elles continuent si l'on passe à une autre offre ou revient à la liste, la ligne affiche alors **« Modifications en cours »** (aussi sur mobile, sous le titre), la page de l'offre rouverte retrouve l'opération ou le brouillon, et un message prévient de la fin (version prête, offre publiée ou erreur) sur la liste ou la page d'une autre offre. Pendant la publication, le formulaire est figé. Quitter la section AO perd cet état (le serveur termine quand même). Côté recruteur, chaque rédaction par l'IA exige un abonnement actif, l'adresse e-mail vérifiée et une place sur le quota du jour (30 par organisation, 300 pour toutes : `AO_PUBLICATION_AI_DAILY_LIMITS`, compteurs `aoRewriteOrg` / `aoRewriteAll`) ; un refus donne la version des règles, la publication reste possible.
- Description d'une offre (formes variées rendues par l'IA : `### Titre`, `**Titre**`, `Libellé :` en ligne, bloc unique) : `src/lib/description-sections.ts` la découpe en sections Contexte / Missions / Profil / Modalités, pour le panneau AO (`src/components/ao/ao-description.tsx`, affichage seulement, aussi utilisé pour l'aperçu de la version publiée) et pour la version des règles de « Préparer la publication » (`descriptionForPublication`, après l'anonymisation : titres `###`, puces `-`, paragraphes courts). La page publique et les publications sociales lisent ce texte tel quel.
- **« Publier sans anonymiser »** (ADR 0020, demande du 2026-10-30) : à côté de « Préparer la publication », même formulaire de relecture rempli avec l'offre telle que reçue (sans IA ni quota), avertissement (client nommé sur l'offre publique, LinkedIn et e-mails aux candidats), case « J'ai relu » obligatoire ; admin et recruteurs, mêmes contrôles. Seules les coordonnées personnelles sont retirées (`rawPublicOffer`, `anonymize.ts` : e-mails, téléphones, lignes « Contact : »), à la préparation et de nouveau à la publication ; les noms connus des expéditeurs et de l'interlocuteur restés dans le texte sont surlignés en rouge à la relecture (`findNames`), pas retirés. L'interlocuteur lu par l'IA fait aussi partie des noms masqués de la version anonymisée. Le serveur anonymise par défaut : il faut `anonymized: false` dans la version envoyée (`parsePublishInput`, `publication-input.ts`, testé).
- **« Synchroniser maintenant » est continu et tourne en arrière-plan** : `AoSyncProvider` (`src/components/ao/ao-sync-provider.tsx`), monté dans le layout admin et le layout recruteur, enchaîne de petits passages (2 e-mails) jusqu'à ce que les boîtes soient lues, selon `afterBatch` (`src/lib/ao/sync-loop.ts`, testé : s'arrête quand tout est lu, IA indisponible, boîte illisible, ou passage sans progrès ; attend puis réessaie si un passage automatique tient la boîte). Le layout restant monté d'une page à l'autre, la synchronisation **continue quand on quitte la page AO** : un bandeau « Synchronisation des appels d'offres en cours · Voir » s'affiche sur les autres pages de l'espace, et la page AO retrouve en revenant la progression, « Arrêter » (fin du passage en cours) et le message de fin. Onglet rechargé : elle reprend (progression dans `sessionStorage`, propre à l'onglet) ; onglet fermé : elle s'arrête après le passage en cours, rien n'est perdu (e-mails lus enregistrés, point de reprise). Passages par des **routes POST** (`/api/admin/candidats/sync`, `/api/recruiter/ao/sync`, cœur `aoSyncResponse` de `src/lib/ao/http.ts` : appelant vérifié, demande venue d'une page du site par `Sec-Fetch-Site`, abonnement actif côté recruteur), **jamais par une Server Action** : le navigateur exécute les Server Actions une par une, et des passages de 2 min enchaînés en arrière-plan retiendraient toutes les autres actions du site. Quand la page AO est affichée, chaque passage envoie ses filtres (`?tableau=`) et renvoie la liste filtrée à jour (`loadAoView`), affichée aussitôt si elle est plus récente que ses données et porte sur les mêmes filtres (`live.version`, `live.view.query`) ; la page est rafraîchie à la fin (`router.refresh()`).
- Une seule synchronisation à la fois par organisation (cron, boutons, `ao:poll`) : verrou en base (document `lock_<empreinte>` de `ao_sync_state`, expiré après 6 min) ; un appel qui arrive pendant un passage de la même organisation est ignoré (`skipped: true`). Le bouton « Synchroniser » et « Réessayer » de `/admin/candidats` ne portent que sur les boîtes de la plateforme.
- Images (PNG, JPEG, GIF, WebP ≤ 5 Mo) et PDF sans texte (scannés) : transcrits par Claude (`claude-opus-5-5`, effort `low`, 8 000 jetons max, repli serveur sur `claude-opus-4-8` en cas de refus), 3 lectures max par e-mail et 50 par jour et par organisation (compteur dans `ao_sync_state`), clé Claude de Config IA (ou `ANTHROPIC_API_KEY`) ; sans aucune clé (ni Claude ni OpenAI), la pièce jointe est ignorée avec la raison. Archives Office vérifiées par décompression réelle bornée (50 Mo), pas d'après les tailles annoncées. Échec passager (API saturée, délai) : `RetryLater`, l'e-mail entier est repris (un report faute de temps ne compte pas comme essai).
- **Tableaux d'offres joints** (xlsx, xls, csv, tsv — tableau de suivi d'AO d'un client, export de cette page) : chaque ligne devient une offre, **sans IA** (`spreadsheet.ts`, règles pures testées avec de vrais en-têtes). Colonnes reconnues par leur nom, dans un ordre qui lève les ambiguïtés (`COLUMNS`) : intitulé (ou en-tête « Nom » seul, sauf à côté d'un prénom ou d'une vraie colonne d'intitulé : liste de personnes), client, lieu, contrat, télétravail, TJM, compétences (toutes les colonnes concernées), durée, démarrage, date limite, expérience ; description = la colonne de description telle quelle, ou une section `### <en-tête>` par colonne (contexte, missions, profil…). Les colonnes de suivi interne (numéro, statut, candidats présentés ou positionnés, notes, taux, date de réception) et celles qui nomment des personnes ou des coordonnées (interlocuteur, manager, référent, acheteur, téléphone…) sont ignorées. En-tête cherché dans les 15 premières lignes (un intitulé + au moins une autre colonne), 500 lignes et 64 colonnes lues au plus par fichier. Fichiers hostiles : contenu vérifié par ses premiers octets (une archive renommée « .xls » ou « .csv » est refusée), décompression bornée, taille annoncée par le fichier ignorée (`readSheets` avec `nodim` et bornes, dans `job-import.ts`) ; pas d'ODS (ses cellules répétées se développent sans limite à la lecture). Même validation que les réponses de l'IA (`parseOfferFields`). Au plus 500 offres de tableaux par jour et par organisation (compteur dans `ao_sync_state`) : au-delà, l'e-mail attend sans user ses essais. Un tableau aux colonnes inconnues, ou sans aucune ligne exploitable, est lu par l'IA comme texte, avec le corps de l'e-mail. Quand un tableau a été lu, le corps de l'e-mail (qui le présente) n'est pas envoyé à l'IA — il en tirerait des quasi-doublons —, les autres pièces jointes si. L'export Excel de cette page se relit à l'identique (client compris s'il est renvoyé par l'un des nôtres ; envoyé d'ailleurs, le client devient l'entreprise de l'expéditeur). Décision : `docs/adr/0003-ao-tableaux-sans-ia.md`.
- **IA indisponible, échecs sans frais** (`ai-failures.ts`, règles pures testées) : compte ou configuration (crédits épuisés, clé refusée, modèle inconnu, non configuré — côté API compatible OpenAI, seule une réponse d'erreur JSON compte) et panne du service (saturé 429/529, erreur 5xx sauf 504, injoignable). Ces requêtes sont refusées avant traitement : rien n'est facturé. Les images et PDF scannés passent alors au modèle OpenAI de Config IA (GPT-4o par défaut, clé OpenAI de Config IA ou `OPENAI_API_KEY`, `extractors/vision-openai.ts`, nom de fichier générique envoyé) ; le texte des e-mails passe déjà aux autres modèles configurés (repli de `callLLM`, qui lève `LLMChainError` avec l'échec de chacun, message inchangé ; `LLMUnreachableError` distingue « injoignable » de « sans réponse dans le délai », `LLMNotConfiguredError` un modèle non configuré). Si tous les services échouent sans frais : `AiUnavailable`, l'e-mail reste « en erreur » avec la cause par service et est repris à chaque synchronisation sans user sa reprise. Un délai dépassé ou une réponse illisible ont pu être facturés : ils suivent la règle normale (une reprise), y compris dans un échec mixte, pour qu'un e-mail ne soit pas refacturé indéfiniment. Lecture des scans impossible : le reste du passage continue, les autres e-mails à scan attendent sans nouvel appel (`PassState`). Extraction des offres impossible : le passage s'arrête. Dans les deux cas `aiUnavailable: true` dans le compte rendu (avertissement dans les logs du cron, message sur `/admin/candidats`, `ao:poll` ne relance pas plus tôt). Une lecture refusée ainsi est rendue au compteur du jour. Le courrier nouveau passe avant les e-mails à réessayer (`processingOrder`). Décision : `docs/adr/0002-repli-ia-credits-epuises.md`.
- E-mails en erreur repris **une seule fois**, au passage suivant (`MAX_ATTEMPTS = 2` dans `attempts.ts`, règle pure testée ; réponse IA tronquée ou message > 25 Mo : abandonnés tout de suite) ; un e-mail en attente de l'IA (échec sans frais, `AiUnavailable`) ou reporté faute de temps ne compte pas d'essai et revient à chaque passage. Bouton **« Réessayer »** sur chaque e-mail non traité de `/admin/candidats` (action `retryAoEmail` ; même bouton côté recruteur, `retryRecruiterAoEmail`) : remet ses essais à zéro (`manualRetryPatch`), même abandonné ou enregistré avant ces règles, **autant de fois qu'on le relance** (décision du 2026-10-26) — côté recruteur, adresse e-mail vérifiée et quota du jour : 30 relances par organisation, 300 pour toutes (`AO_RETRY_DAILY_LIMITS`, compteurs `aoRetryOrg` / `aoRetryAll`, place prise avant la remise à zéro, une relance qui échoue compte) —, puis le traite tout de suite (`syncAoEmail` : même traitement et même verrou qu'une synchronisation, sans toucher au point de reprise) ; si une synchronisation est en cours ou que ce traitement échoue, il reste en file pour la suivante. Pièces jointes zip > 50 Mo décompressées ignorées ; 50 offres max par e-mail ; données AO supprimées après 365 jours (les offres publiées restent).
- Vercel Cron ne s'exécute que sur la production ; sur une preview `dev`, utiliser le bouton « Synchroniser maintenant ». En local : `npm run dev` (ou `npm run dev:local` si Appwrite répond en « fetch failed (ETIMEDOUT) » : réseau sans IPv6 / serveur à plus de 250 ms) puis `npm run ao:poll` (même appel toutes les `AO_POLL_INTERVAL_MINUTES` minutes, 5 par défaut, ou `--every N` ; `--once` pour un seul passage ; en arrière-plan : `npm run ao:poll:start` / `ao:poll:status` / `ao:poll:stop` ; `CRON_SECRET` ≥ 16 caractères dans les fichiers .env lus par `next dev`). Hors Vercel, n'importe quel planificateur peut appeler `GET /api/cron/ao-inbox` avec `Authorization: Bearer $CRON_SECRET`.
- Variables : `AO_CREDENTIALS_KEY` (32 octets base64, serveur seulement ; la changer rend les mots de passe enregistrés illisibles), `APPWRITE_COLLECTION_AO_EMAILS` / `_AO_OFFERS` / `_AO_STATE` / `_AO_SOURCES` / `_AO_OFFER_DETAILS` / `_AO_OFFER_INDEX`, `CRON_SECRET` (≥ 16 caractères), `AO_IMAP_*` (lues seulement par `ao:migrate-sources`) — voir `.env.example`.

# Assistant IA (module portable)

- **Module `src/assistant/`** (ADR 0007, guide d'intégration `src/assistant/README.md`) : n'importe rien de l'application (règle ESLint) ; le cœur (`core/`) ne dépend d'aucun framework, la fenêtre (`react/`) pas de Next.js. Le site fournit ses adaptateurs `AssistantHost` : pour MyBestConsultant `src/lib/assistant/host.ts` (`server-only`), actions `src/lib/assistant-actions.ts`, fenêtre `src/components/assistant/mbc-assistant.tsx` dans les layouts candidat et recruteur, variables de style `.mbc-assistant` dans `globals.css`.
- **Périmètre v1** : candidats et recruteurs connectés **à l'adresse e-mail vérifiée** (inscription libre : sinon des comptes jetables épuiseraient le quota de la plateforme) ; réponses tirées seulement de `src/lib/assistant/knowledge.ts` (à mettre à jour quand une page, un libellé ou une règle change), aucun accès aux données de l'utilisateur, aucun outil. « Transmettre au support » crée un ticket du Help Desk avec la conversation (après confirmation ; limite de 10 demandes ouvertes inchangée ; lignes suivantes d'un message préfixées « › » pour qu'un utilisateur ne puisse pas écrire une fausse réponse « Assistant : »). - **Modèle** : ligne « Assistant IA » de Config IA, **sans repli** (`callLLM` avec `strict: true`) pour que les conversations n'aillent qu'au modèle choisi. En mode strict, `callLLM` refuse aussi l'appel quand Config IA est illisible ou quand le modèle choisi a été retiré ou désactivé (`LLMNotConfiguredError`) ; panne = message d'erreur. Par défaut : le modèle par défaut de Config IA.
- **Quotas** (`takeDailySlot`, compteurs `assistantUser` / `assistantAll` dans AO_STATE) : 30 messages par utilisateur et par jour (UTC), 1 000 pour la plateforme (`ASSISTANT_DAILY_LIMITS` ; message distinct et avertissement dans les journaux quand la plateforme est au plafond). Un message refusé par une panne du modèle compte quand même. Message de 2 000 caractères au plus, 10 derniers échanges et 12 000 caractères d'historique envoyés au modèle, réponse coupée à 8 000 caractères sans couper un emoji (`src/assistant/core/rules.ts`, testé).
- **Données** : collection `assistant_turns` (5/16 attributs, sans permission client), un document par échange, enregistré seulement après la réponse (enregistrement impossible : réponse affichée avec un avertissement, non reprise) ; toute lecture filtre sur l'utilisateur de la session (conversation d'un autre = « introuvable »). Supprimés après **30 jours** (`ASSISTANT_RETENTION_DAYS`, décision du 2026-10-23 ; durée annoncée dans la fenêtre et dans le contenu d'aide) par `/api/cron/assistant-purge` (Vercel Cron, quotidien, 5 min au plus ; purge aussi les places de quota de plus de 7 jours) et avec le compte : `deleteUserAccount` (avant le compte, puis second passage après) et `removeMember` (retrait d'un membre d'équipe).
- **Deux variables** : `APPWRITE_COLLECTION_ASSISTANT_TURNS` (collection : la purge et la suppression avec le compte en dépendent, **ne pas la retirer** tant qu'elle contient des conversations) et `ASSISTANT_ENABLED=true` (affiche l'assistant ; le masquer = retirer celle-ci).
- **Mise en place** : `npm run assistant:setup -- .env.dev` (simulation), puis `--apply` sur DEV ; variables en portée **Preview** de Vercel et dans un fichier local qui vise `bestconsultant-dev`, test sur la preview `pre-dev`. Production : un humain sauvegarde la base, lance `--prod` puis `--prod --apply`, et seulement ensuite définit les variables en portée Production et redéploie (variable définie sans collection : l'assistant échoue). Retour arrière complet : exporter si besoin, puis supprimer la collection dans la même opération que le retrait de la variable ou du code.

# Vivier général des recruteurs (matching automatique)

- **`/recruiter/vivier`** (décision du 2026-10-28) : en plus du vivier de chaque offre (inchangé, `/recruiter/vivier/[jobId]`), un **vivier général** où le recruteur dépose des CV sans choisir d'offre. Même import (navigateur → bucket `VIVIER_CVS`, puis `attachVivierCv(null, …)`), mais dans une fenêtre (« Importer des CV », demande du 2026-10-28 : la zone de dépôt ne doit pas repousser la liste des offres ; l'import continue fenêtre fermée). La page a deux onglets, « Viviers par offre » (vue par défaut) et « Vivier général » (`vivier-tabs.tsx`, même demande) : une vue à la fois, l'autre masquée mais montée (import et synchronisation continuent), vivier général gardé dans l'adresse (`?vue=general`), même confidentialité (CV visibles de celui qui les a importés ; tous ceux de l'organisation pour un admin), mêmes fiches. Un CV du vivier général est un document `vivier_cvs` **sans `jobId`** (`Query.isNull('jobId')`) ; `matchScore` / `matchReason` y restent vides (ils sont ceux du vivier d'une offre). Les lectures plafonnées des viviers d'offres (tableau de bord, annonces, reporting, compteurs de `/recruiter/vivier`) excluent le vivier général (`Query.isNotNull('jobId')`) : un import massif les remplirait. **Fichier envoyé par le navigateur** (bucket sans session, donc sans propriétaire) : `attachVivierCv` n'accepte qu'un fichier envoyé depuis 15 minutes au plus et rattaché à aucun CV (`assertFreshUpload`, index `cvFileId_idx`) ; « Supprimer » garde un fichier encore rattaché à un autre CV. CV ou offre d'un autre = « introuvable », comme s'ils n'existaient pas. « Analyser à nouveau » est refusé pour un CV déjà analysé.
- **Matching automatique** : après la création du profil, le CV est comparé par l'IA aux **offres ouvertes de l'organisation** (`getOpenJobsOfTenant` : actives, non expirées, sans celles de la plateforme), 5 offres par appel en parallèle, **numérotées 1 à 5** et non désignées par leur identifiant (2026-11-04 : un identifiant mal recopié par l'IA rattachait une note à une autre offre), les 100 plus récentes (toutes celles que lit `getOpenJobsOfTenant`, pour qu'un CV qui correspond déjà à une offre ait été comparé à toutes les autres). Seul le parcours professionnel part à l'IA (postes avec employeur, période et missions, compétences, résumé, années, langues ; `profileForAi`), **jamais le nom ni les coordonnées**, chaque champ borné (une offre aux centaines de compétences ne fait pas un appel de la taille du contexte, testé). Modèle : celui du « Matching IA » de Config IA, ou **Claude** s'il n'y en a pas (`callLLM` option `moduleDefault`, `pickPrimary` testé), repli habituel s'il échoue. Un CV **correspond** à une offre notée 65 ou plus (`SOURCING_MIN_SCORE`). Scores enregistrés sur le CV, attribut `offerMatchesJson` (JSON : offre, score, raison pour les 10 meilleures ; offres fermées retirées à chaque écriture) ; relu juste avant l'écriture, ce qui réduit à quelques millisecondes la fenêtre où deux comparaisons simultanées du même CV s'effacent (les offres perdues redeviennent « nouvelles »). Règles pures : `src/lib/vivier-matching.ts` (testé) ; appel : `scoreCvAgainstOffers` (`matching-core.ts`) ; actions : `src/app/recruiter/vivier/actions.ts` (partagées par les deux pages, organisation et propriétaire du CV vérifiés à chaque action par `ownVivierDoc`).
- **Offres correspondantes** : sur chaque carte du vivier général, chaque offre de « Correspond à » ouvre le détail de l'offre publiée (`/jobs/<id>`, qui affiche « Connecté en tant que recruteur » à la place de « Postuler ») dans un nouvel onglet, sans ouvrir le profil : l'import et la synchronisation des CV tournent dans la page du vivier (demande du 2026-10-29 ; avant : le pipeline de l'offre). « Format ESN » et « Modèle CV » : voir « Export des CV au format ESN » (ADR 0016).

Toutes les listes de la page lues en entier (`listAllDocuments`, `listAllByValues`), plus de plafond à 200. **Mise en place** : `schema:push -- dev`, variable `APPWRITE_COLLECTION_VIVIER_OFFER_MATCHES`, `vivier:matches --apply`, déploiement, de nouveau `--apply` ; sans la collection, Matching IA, comparaison et suppression d'un CV du vivier général échouent. Fiche (`/recruiter/candidate-preview/vivier/<id>`) et CV (`/api/vivier-cv/<fichier>`) ouverts au seul recruteur qui a importé le CV ou à un admin de son organisation, comme la page du vivier (`ownVivierDoc`) ; sinon introuvable (avant : CV lisible par tout recruteur de toute organisation). « Ajouter dans le funnel » refuse le CV d'un collègue. Actions de la page (`matching-actions.ts`) : offre de l'organisation ou de la plateforme vérifiée par chacune (`recruiterCanOpenJob`, `job-ownership.ts`, testé ; avant, n'importe quelle offre par son identifiant), « Ajouter dans le funnel » refuse un CV d'une autre organisation ou du vivier d'une autre offre. **Sécurité** (revue du 2026-11-03) : l'adresse e-mail d'un CV du vivier, écrite par celui qui l'importe, ne rattache la candidature qu'à un profil de **candidat** existant, sans rien écrire dans ce profil (CV du vivier joint à la candidature) ; une adresse d'un autre rôle ou d'un compte de connexion sans profil est refusée (avant : rattachement à n'importe quel compte, CV d'autrui lisible ou fichier déposé sur son profil). « Base candidats » : seulement un candidat proposé pour l'offre (`job_matches`) et de rôle candidat. - **Notation d'un candidat pour une offre** (demandes du 2026-11-03 — un 95/100 sans l'expérience du domaine demandé — et du 2026-11-04 — scores qui changeaient à chaque « Rafraîchir », un 85 qui ne correspondait pas au CV du candidat ; ADR 0028) : règles communes aux quatre notations — candidature (`scoreApplicationInternal`, screening), base candidats (`matchCandidatesForOffer`), vivier d'une offre (`matchVivierCvAgainstJob`), vivier général (`vivierMatchingPrompt`) — dans `src/lib/match-scoring.ts` (testé). **L'IA ne donne plus de note** : elle compare les **expériences du CV** (postes, missions, projets, employeurs, durées) à l'offre, et **ses preuves sont des citations du CV, vérifiées par le code** (`verifiedRole`, `verifiedEvidence`, testés ; 2026-11-04, cas de production vérifié avec `matching:explain` : un expert sécurité applicative noté 66 parce que l'IA comptait un poste « en environnement agile » comme Scrum Master et citait la liste des compétences) — pour chaque métier du titre, `intitule` = l'intitulé exact d'un poste du CV (sans intitulé : « non » ; absent du CV : un niveau de moins), puis **une seconde question à l'IA, étroite, compare les intitulés** (`titleCheckPrompt`, `withCheckedTitles` dans `src/lib/title-check.ts`, une seule question par notation) : même métier, jugement gardé ; même famille (« Ingénieur DevOps » pour « Ingénieur sécurité »), « partiel » au plus ; autre métier, « non » ; comparaison impossible, « partiel » au plus — **règles générales, sans liste de mots ni d'intitulés propre à un domaine** (demande du 2026-11-04 : généraliser) ; pour une exigence ou une compétence « oui », `citation` = une ligne d'expérience d'au moins 5 mots retrouvée dans le CV, pas une liste de mots-clés, et qui nomme la compétence (sinon « partiel ») ; elle juge d'abord `"poste"` — **le titre de l'offre est la référence** (demande du 2026-11-04) : le candidat a-t-il exercé ce métier (oui / partiel / non) ? des compétences partagées avec un autre métier ne font pas le poste ; un titre à plusieurs métiers (« Scrum Master et Développeur Full Stack ») est jugé **métier par métier**, et un métier non exercé plafonne le score sans se compenser par l'autre (un Scrum Master qui n'avait jamais développé était noté 85 sur cette offre) —, puis `"exigences"` (une par **exigence tirée de la description** par le code, `offerRequirements` : puces du profil recherché puis des missions, 10 au plus, les mêmes pour tous les candidats ; sans liste, un jugement d'ensemble), puis `"domaine"` (expérience du domaine exigé, prouvée par le parcours et jamais par une compétence ou un mot-clé : oui / partiel / non / non requis), `"competences"` (une valeur oui / partiel / non par compétence demandée de l'offre, liste numérotée de 12 au plus, `requiredSkills` ; sans liste, un jugement d'ensemble) et `"niveau"` (oui / partiel / non / non précisé) ; **le code calcule le score** (`judgedScore` : poste 30, exigences 30, compétences 20, domaine 15, niveau 5 — niveau compté sur les expériences du même métier, pas toute la carrière —, `SCORE_WEIGHTS`) puis plafonne (`capFor`, le plus bas des deux : poste non exercé = 50 au plus, voisin = 75, `ROLE_CAP` ; domaine absent = 60, voisin = 80, `DOMAIN_CAP` ; tous sous le seuil « correspond » de 65, l'e-mail automatique de 70 et le top 5 du sourcing quand le critère manque). Réponse sans jugement lisible : pas de score (le candidat reste à noter), jamais un score inventé. La raison affichée commence par le résumé des jugements (« Poste : oui · Exigences : 4 sur 6 · Compétences : 6 sur 9 · Domaine : non · Niveau : oui — … », `judgementSummary`) ; la recommandation d'une candidature suit le score (`recommendationFor`). Les bonus des recommandations ne font jamais passer le seuil de 65 à un candidat noté en dessous (`withBonus`). Description de l'offre envoyée avec le **profil recherché d'abord** (`offerTextForAi`, 4 000 caractères ; 1 500 par offre pour le vivier général) ; **CV lu jusqu'à 12 000 caractères** (`CV_CHARS_FOR_SCORING`, avant 3 000 pour la base et 5 000 pour les candidatures). **Base candidats : un appel d'IA par candidat** (5 à la fois, `mapLimit`, `src/lib/concurrency.ts`), 30 candidats par passage, les plus récents d'abord (avant : 30 par appel désignés par leur identifiant, choisis sans ordre parmi les 200 premiers). **« Rafraîchir (nouveaux candidats) »** note seulement les candidats pas encore notés pour l'offre, sans toucher aux autres scores (`runPoolMatching(…, 'new')`), en passant les CV illisibles (3 tours au plus) ; **« Recalculer tout »** (confirmation) renote les candidats déjà notés, 120 au plus (`'all'`, aussi « Recalculer » d'un AO publié ; sans note enregistrée, les 30 plus récents). Notes écrites ligne par ligne (`planPoolRows`, `src/lib/pool-matching.ts`, testé) : **une note n'est jamais supprimée parce que son nouveau calcul a échoué**, seuls partent les candidats qui ne sont plus à noter (désinscrits, CV retiré, candidature envoyée) ; identifiant fixe par offre et candidat (`poolRowId`) : deux passages simultanés n'écrivent qu'une ligne. Le compte rendu (candidats notés, CV non notés) s'affiche sur la page (`maxDuration = 300`) et dans la section Sourcing d'un AO, à côté des résultats. La température ne se règle pas sur les modèles Claude actuels (paramètre refusé) : la stabilité vient des jugements, pas d'un réglage. **Vérifier un score contesté sans rien écrire** : `npm run matching:explain -- <env> [--prod] --job <offre> --cv <fichier CV>` (identifiant de `/api/cv/<id>`) note le CV avec exactement le code de l'application (`cvScorer`, `sourcing-core.ts`, partagé avec la base candidats), affiche chaque jugement et sa preuve, le score calculé, son plafond, et le score enregistré aujourd'hui ; un appel d'IA, aucune écriture. Les scores déjà enregistrés ne changent pas : « Recalculer tout » pour la base candidats, « Relancer » sur la carte d'une candidature (Matching IA) ; les CV des viviers ne sont pas renotés automatiquement. **L'e-mail automatique au candidat** (score de 70 ou plus) part à la **première analyse** de la candidature seulement (une analyse relancée ou le screening de toutes les candidatures ne le renvoient plus) et ne contient que le résumé de l'IA (`plainSummary`), jamais les jugements internes.
- **« Sans offre correspondante »** (bouton et fenêtre `unmatched-cvs.tsx`) : CV au profil créé sans aucune offre ouverte à 65 ou plus, avec le nombre d'offres ouvertes jamais comparées ; « Synchroniser » compare chacun, l'un après l'autre (`syncVivierCvMatching`), aux seules offres nouvelles pour lui ; « Arrêter » après le CV en cours ; arrêt au premier refus ou échec (appel interrompu compris). Les nouvelles offres ne sont pas comparées automatiquement aux CV existants, ni par « Synchroniser » aux CV qui correspondent déjà à une offre (demande du 2026-10-28 : synchronisation à la main, des CV sans correspondance). Un lot en échec sur un CV qui correspond déjà à une offre laisse ces offres non comparées (message distinct, `partial`). Les actions du vivier général ne relisent pas la page (`revalidateVivier`) : la liste vit dans l'état du client, qui se met à jour.
- **Coût** : chaque comparaison d'un CV (quel que soit le nombre d'offres) exige l'adresse e-mail vérifiée et prend une place sur les quotas du jour : 200 par organisation, 2 000 pour toutes (`VIVIER_MATCHING_DAILY_LIMITS`, compteurs `vivierMatchOrg` / `vivierMatchAll` dans AO_STATE, purgés avec les autres) ; une comparaison qui échoue compte. Refus et échec : le CV est importé quand même et le message s'affiche ; sans offre correspondante, il apparaît dans « Sans offre correspondante ». `takeDailySlotId` refuse sans écriture quand toutes les places du jour sont prises.
- **Mise en place** : attribut `offerMatchesJson` (texte, 20 000) et index `cvFileId_idx` de `vivier_cvs` (12/16 attributs), dans `appwrite.config.json` : `npm run schema:push -- dev` avant de déployer sur la preview ; production : `schema:check -- prod` puis `schema:push -- prod` **par un humain** avant la mise en production. Sans l'attribut, l'import dans le vivier général réussit mais chaque comparaison échoue après l'appel à l'IA (message « La comparaison aux offres n'a pas abouti », « Unknown attribute » dans les journaux).

Un AO affecté passe son recruteur à l'offre publiée (`publishAoOfferOf`), et changer l'un change l'autre ; une offre créée au tableau de bord n'a pas d'AO (identifiant sans « ao »), seule l'offre change. **À la création** (demande du 2026-11-02) : toute offre créée par quelqu'un (« Créer une offre », imports, publication d'un AO, import et LinkedIn de l'admin) est affectée à son auteur, sauf AO déjà affecté (son recruteur) : `jobOwnership` (`src/lib/job-ownership.ts`, testé) écrit `postedBy` et `recruiterId` = **profil** (`users.$id`), donc `recruiterId === postedBy`. Offres partagées de la plateforme : pas d'affectation dans « Mes offres ». **E-mail** (demande du 2026-11-02) : le nouveau recruteur est prévenu (lien vers le matching de l'offre, ou vers la page de l'AO), celui qui affecte **en copie** (`notifyAssignee`, Appwrite Messaging : destinataire = compte Auth, copie = cible e-mail du compte de celui qui affecte) ; ni pour un retrait, ni pour le même recruteur, ni pour une affectation à soi-même (`shouldNotifyAssignee`, contenu `assignmentEmail` : `src/lib/assignment-email.ts`, testé). Une affectation, un seul e-mail : la synchronisation AO ↔ offre et la reprise à la publication n'en envoient pas. E-mail ou copie non partis : affectation gardée, message affiché sous le choix, cause dans les journaux (`[affectation]`). **Mise en place** : attribut `assigneeId` (texte, 36) de `ao_offer_details` (7/16) dans `appwrite.config.json` : `npm run schema:push -- dev` avant de déployer ; production : `schema:check -- prod` puis `schema:push -- prod` **par un humain**. Sans l'attribut, l'affectation d'un AO échoue avec un message, le reste fonctionne.
- **Scripts sur les offres** (demande du 2026-11-02 ; simulation par défaut, `--apply` pour écrire, `--prod` pour la production, à lancer par un humain, qui tape l'identifiant du projet pour confirmer) : `npm run jobs:move-tenant -- <env> --from <organisation> --to <organisation>` fait passer toutes les offres d'une organisation dans une autre (`jobs.tenantId` seulement). Candidatures, présélections, CV du vivier, correspondances IA, publications, pipelines et AO d'origine gardent l'ancienne organisation (comptés à l'écran), **mais les pages d'une offre (pipeline, matching) vérifient l'organisation de l'offre puis lisent ces données par offre** : la nouvelle organisation voit les candidats des offres déplacées, l'ancienne ne peut plus les ouvrir. À ne lancer que si les deux organisations sont la même entreprise. `npm run jobs:fill-recruiter -- <env>` affecte à leur auteur (`postedBy`) les offres sans recruteur et convertit en profil les `jobs.recruiterId` et `ao_offer_details.assigneeId` écrits en compte Auth avant l'ADR 0023 (recruteur introuvable, auteur introuvable ou hors de l'organisation de l'offre : laissé et compté ; identifiants écrits affichés pour un retour arrière ; sauvegarde aussi `ao_offer_details` s'il convertit un AO), à lancer **après** `jobs:move-tenant` et, en production, juste après le déploiement du code de l'ADR 0023. Avant d'écrire, chacun sauvegarde la collection `jobs` dans `jobs_backup_JJMMAAAA` (jour de Paris ; `src/lib/appwrite/collection-backup.ts`, testé) : mêmes attributs (facultatifs ; 18 attributs, au-delà de la règle des 16, accepté par le serveur comme pour `users`), mêmes `$id` et permissions, dates d'origine dans `originalCreatedAt` / `originalUpdatedAt`, collection sans permission ; un document déjà sauvegardé n'est pas réécrit (deux scripts le même jour : l'état d'avant le premier). Les collections `*_backup_JJMMAAAA` ne sont jamais reprises dans `appwrite.config.json` par `schema:pull` (ni donc créées en production). Production : dump de la base d'abord (la sauvegarde est sur le même serveur). Retour arrière : déplacement = `tenantId` relu dans la sauvegarde au même `$id` ; affectation = `recruiterId` remis à vide sur les offres listées. **Supprimer la sauvegarde** (console Appwrite) une fois le résultat vérifié, au plus tard 30 jours après (copie de données d'offres, RGPD).
